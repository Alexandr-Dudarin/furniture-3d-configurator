# Передача пяти комодов в основной проект — пакет v2

Дата: 20 сентября 2026. Это облегчённая замена `furniture-3d-configurator-dressers-10-14-review.zip`. Архив содержит только модели 10–14, исходники, конфиги, тесты, референсы и отчёты. Все пути указаны от корня проекта.

**Задача для чата основного проекта:** перенести модели в актуальную ветку, подключить их к общим каталогам мебели и покрытий, реализовать общую affine UV-компенсацию, проверить в браузере. Не ограничиваться добавлением пяти пунктов в список. Геометрия уже проверена, но полный выбор отделок и корректный рисунок при изменении размеров требуют интеграции в движок.

- Геометрия, иерархия узлов, материалы, UV, имена, исходные размеры, диапазоны и `resizeRules` сохранены. Конфиги и `model-contract.json` побайтно совпадают с v1.

## 5. Каталог покрытий и независимая смена материалов

Связанные общие файлы: `src/three/materials/materialRegistry.ts`, `types.ts`, `createMaterial.ts`, `materialController.ts`; тип слотов — `src/three/furniture/types.ts`.

Каждый модельный `config.ts` экспортирует `MATERIAL_TARGETS`:

| Группа | Что менять |
|---|---|
| `carcass` | Корпус и внутренние детали, включая короба ящиков |
| `fronts` | Двери, фасады ящиков, рёбра и угловой декор |
| `hardware` | Наружные ручки; у модели 10 группа пустая |
| `fixed` | Направляющие, петли, подпятники; не включать в слоты корпуса/фасадов/ручек |

Создать раздельные `materialSlots.carcass` и `.fronts`, указать `targets`, `defaultFinish`, `allowedFinishes`. У моделей с ручками добавить `.hardware`. Defaults должны существовать в registry и входить в allowed list. Модель 10 не должна показывать пустой выбор ручек.

Функция `createMaterialReviewDefinition` в каждом config — помощник для review. В текущей версии её список hardware ограничен `metal-black-matte`, `metal-white-matte`, `metal-anthracite`. Для латуни Норда расширить разрешённые hardware-покрытия либо собрать конечные слоты декларативно в конфиге. Не передавать новый brass ID в прежний helper: он намеренно бросит ошибку. Список доступных покрытий не следует делать зависимым от `modelId` внутри общего controller.

Во входном каталоге отсутствуют настоящие неметаллические ЛДСП/глянец/кашемир и латунь. Сначала проверить, не добавлены ли они уже в актуальной ветке, и использовать существующие ID. Для ровного цвета новый PNG/JPG не нужен. `MaterialFinishCategory` в snapshot содержит только `wood | stone | metal`; добавить подходящую категорию плит и согласовать UI категорий, если это требуется новой схемой каталога. ## 6. Обязательная общая доработка UV

`assets/source/<Model ID>/model-contract.json` содержит **`uvContract` по имени каждого материала**, включая торцы, рёбра Марвэла и вырезы Байкала. Перенести эти данные в декларативное поле `FurnitureDefinition`, согласованное с актуальным API движка. JSON исходников не должен становиться случайной HTTP-зависимостью страницы; импортировать данные при сборке или генерировать типизированный config.

Для каждой оси `u` / `v` заданы `dimension`, `baseLength`, `stretchFactor`, `translationFactor`, `anchor`. Применение:

```text
delta  = currentDimension - baseDimension
factor = (baseLength + delta * stretchFactor) / baseLength
repeat = initialRepeat * factor
offset = initialOffset
       + initialRepeat * (anchor * (1 - factor) + delta * translationFactor)
```

`u` соответствует `texture.repeat.x/offset.x`, `v` — `.y`. Размерности заданы в метрах. Базовые repeat/offset захватывать один раз для конкретного нового экземпляра текстуры, не от уже изменённого предыдущим resize значения. Материал после замены должен получить актуальные размеры через `controller.refreshTextures`; не умножать накопленный коэффициент повторно.

Применять согласованное преобразование к Base Color, Normal, Roughness, Metalness и другим используемым картам. Несколько свойств материала могут ссылаться на один объект Texture: не применять преобразование дважды. При разных UV bindings нужны разные экземпляры Texture с общим источником изображения; объединять все semantic materials или их repeat/offset в один объект нельзя. Замена картинки одной текстуры не должна менять покрытие соседнего слота или другой модели.

У движущихся кромок `stretchFactor=0`, но `translationFactor` может быть ненулевым: только repeat недостаточно. Число и сечение декоративных элементов сохраняются; масштабировать целую группу для обхода этих правил нельзя.

Старый `textureAxes` рассчитывает отношение общего габарита, а не полезной длины детали. Поэтому в этих конфигах он намеренно пуст. Не заполнять его `legacyTextureAxes` из JSON как готовое решение. Пример №13: при высоте 0.9 → 1.1 м фасаду нужен repeat V **1.252397779**, старое API даёт **1.222222222**. Тест геометрии может быть зелёным при неверном рисунке.

`prepare_checks.mjs compatibility` сейчас ожидаемо возвращает **2 / REQUIRES_ENGINE_EXTENSION**. Это отдельная диагностика ограничения старого API. После новой реализации добавить проверки именно нового API; сама legacy-проба не начнёт проверять его автоматически. Нужны полезные длины, фаза на стыках, min/mid/max/return, дерево на корпусе/фасадах/торцах и последовательность resize → смена покрытия → resize → возврат.

У исходных `oak-natural/oak-grey` волокна направлены по V, у `walnut-natural` — по U. Согласовать ориентацию в общей библиотеке или в общем механизме материала. При повороте учитывать tangent-space normal map вместе с цветом и шероховатостью.

## 7. Размеры, интерфейс и подготовленные механизмы

Единицы — метры; X — ширина, Y — высота, Z — глубина; передняя сторона +Z. По X/Z модель центрирована, пол Y=0. Высота регулируется, толщины фиксированы: основные плиты 16 мм, задняя стенка 4 мм, дно ящиков 6 мм. Радиус кромки 0.7 мм, размеры ручек, зазоры и декоративные сечения сохраняются.

| № | Ширина, мм | Высота, мм | Глубина, мм | Ящики / двери / полки |
|---|---|---|---|---|
| 10 | 500–1000 | 700–1050 | 300–500 | 4 / 0 / 0 |
| 11 | 1000–1600 | 750–1100 | 350–600 | 4 / 1 / 1 |
| 12 | 1200–2000 | 550–900 | 350–600 | 6 / 0 / 0 |
| 13 | 1200–2000 | 750–1100 | 350–600 | 4 / 2 / 2 |
| 14 | 350–600 | 900–1200 | 300–500 | 5 / 0 / 0 |

Шаг — **1 мм**. Отображение через `toFixed(2)` в метрах скрывает шаг; использовать миллиметры или достаточную точность. Диапазоны и скрытые конструктивные размеры — проектные допущения, а не подтверждённая заводская опция. Для модели 10 принята общая глубина 350 мм из карточки, 330 мм на схеме трактуется как глубина корпуса. Остальные глубины — закрытый габарит с выступающей ручкой.

Двери имеют отдельные pivots, ящики — группы для движения по +Z. Открытые изображения являются техническими позами. Интерактивное открывание, ограничения столкновений и изменение числа полок/ящиков не добавлены. Пока такой общей функции нет, держать модели в закрытом состоянии в UI. Перед обычным resize сбрасывать вручную выставленную техническую позу: resize controller не является reset контроллером анимации.

## 8. Проверки и воспроизведение

Во входном snapshot повторно выполнены **64 теста / 15 файлов**: 34 теста прежних столов и 30 модельных тестов комодов. В v1 было 71/16, потому что тогда в рабочую копию также входила модель шкафа 09. В восстановленном snapshot этого отдельного пакета нет; семь проверок шкафа не удалялись из комодного пакета. В актуальной ветке число тестов может быть больше.

`npm run build` прошёл; осталось исходное предупреждение о JS bundle >500 kB. Все пять GLB: 0 errors / 0 warnings. У 13/14 по три информационных сообщения `URI_GLB`, ожидаемых из-за общих внешних изображений. Validator читает реальные JPEG. Сравнены геометрические bufferViews, узлы, материалы и конфиги v1/v2; геометрия побайтно совпала. Повторная генерация пяти GLB детерминирована.

Повторно отрендерены базовый и максимальный размеры двух изменённых GLB: все четыре изображения попиксельно совпали с v1. Остальные превью сохранены из v1; данные всех девяти состояний каждой модели заново получены из production controllers и совпали. Browser WebGL, GPU FPS и Blender export/reimport здесь не выполнялись. Скрипт Blender приложен; его синтаксис проверен.

Blender 4.x: `blender --background --python assets/source/dresser-13-marvel-fluted/create_model.py`. Он собирает редактируемую сцену из `mesh-source.json`, читает общие карты и создаёт контрольный экспорт. Контрольный GLB Blender может снова упаковать изображения внутрь; для финального облегчённого файла использовать `build_model.mjs` с `externalize_images.mjs`.

Итоговая приёмка в актуальном конструкторе:

1. Пять моделей видны по стабильным ID; работают базовые размеры и отдельные изменения W/H/D с шагом 1 мм, все сочетания min/mid/max и возврат. Толщины, ручки, зазоры и пол сохраняются.
2. Корпус, фасады и ручки меняются независимо; механизмы не перекрашиваются. Стартовые отделки и возврат к ним проверены отдельно. Нет лишнего слота ручек у №10.
3. После внедрения нового UV API рисунок сохраняет физический размер и фазу на всех поверхностях; проверена смена отделки при уже изменённых габаритах и переход между моделями.
4. В браузере нет 404 по картам, ошибок загрузки/шейдеров и мерцания стыков; осмотрены база, максимум, торцы и декор. Оценены draw calls, память и FPS на целевом устройстве. При многократном переключении нет накопления геометрии/материалов/текстур.
5. Прежние столы и шкафы проходят свои тесты. Общая реализация не содержит специальных `if (modelId)` для этих пяти комодов. Изменения registry, каталога и UV оформлены в актуальном основном проекте.
