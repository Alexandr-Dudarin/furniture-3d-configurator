# Стандарт 3D-ассетов мебели v2.21

**GLB-ассеты для мебельного конфигуратора на React + TypeScript + чистом Three.js**

Статус: стандарт проекта  
Актуальность: Furniture 3D Configurator, шкафы 07–09/15 и комоды 10–14; сменные фасады всех девяти моделей, раздельные ракурсы и прямая модульная гардеробная, 28 сентября 2026
Режим параллельной работы: model-only Work-чаты возвращают ZIP-пакеты; центральный integration-чат возвращает проверенный интеграционный ZIP либо Git bundle при работе с репозиторием  
Область применения: столы, шкафы, комоды, тумбы, стеллажи, стулья и другая конфигурируемая мебель  
Главный принцип: **модель проектируется не только исходя из того, как она выглядит, но и исходя из того, как runtime-код должен управлять ею.**

При передаче задачи в новый Work-чат этот файл используется вместе с:

- актуальным Git bundle/архивом проекта без `node_modules`;
- референсами конкретной модели;
- известными физическими размерами и диапазонами конфигурации;
- отдельным названием feature-ветки и уникальным `modelId`.

Work-чат обязан сначала прочитать стандарт и реальный код проекта, а затем определить runtime-контракт модели. Этот документ не разрешает переписывать generic engine или добавлять model-specific условия.

Если Work-чат создаёт только новые модели параллельно с основной разработкой, его итоговым результатом является **model package ZIP, а не Git bundle**. Такой ZIP пользователь не распаковывает в рабочий проект самостоятельно: он передаёт архив центральному integration-чату, который подключает модель к актуальному `main`, обновляет registry, запускает общие проверки и только затем возвращает интеграционный пакет. Для текущего Windows-проекта используется ZIP с относительными путями и командами отдельного коммита.

## 1. Назначение

Каждая production-модель по умолчанию создаётся как **constructor-ready asset**, а не просто как визуальная модель для Blender.

Constructor-ready asset должен быть пригоден для:

- редактирования и проверки в Blender;
- загрузки через Three.js / `GLTFLoader`;
- программного изменения разрешённых размеров;
- перемещения отдельных деталей и сборок;
- замены материалов;
- сохранения физического масштаба текстур при изменении размеров;
- будущих состояний и вариантов конфигурации;
- повторного использования в других сценах и проектах.

Если модель не предполагает конфигурационное поведение, она явно помечается как `static-ready`.

Готовый предмет мебели в этом проекте концептуально состоит из пары:

```text
GLB asset
+
FurnitureDefinition / config модели
```

GLB содержит геометрию и стабильную семантическую структуру.  
TypeScript-конфигурация описывает, как конфигуратор имеет право управлять этой структурой.

## 2. Нельзя определять поведение конфигуратора только по фотографии товара

До начала моделирования необходимо отдельно определить поведение модели **в нашем конфигураторе**, независимо от того, как ведёт себя реальное изделие на фотографиях или в карточке магазина.

Например, карточка товара может показывать только увеличение длины, а наш конфигуратор в дальнейшем может разрешать изменение и длины, и ширины.

Аналогично реальный стол может увеличиваться за счёт вставной доски, тогда как в нашем конфигураторе тот же размер может отображаться как непрерывное корректное изменение поверхности без симуляции физического механизма вставки.

Поэтому перед моделированием каждой модели необходимо определить:

- ID модели;
- базовые внешние размеры;
- все размеры, которые наш конфигуратор может изменять;
- минимальные и максимальные значения;
- resize anchor для каждого размера;
- какие детали масштабируются;
- какие детали перемещаются;
- какие детали остаются неподвижными;
- какие детали расходятся в стороны;
- какие детали могут появляться или исчезать;
- должен ли контур/профиль сохранять радиус или форму;
- какие материалы заменяемы;
- UV-поведение каждой изменяемой поверхности;
- разделены ли поверхности столешницы по несовместимому UV-поведению;
- должна ли модель поддерживать текущую или будущую настройку высоты;
- должна ли модель поддерживать текущую или будущую настройку толщины столешницы;
- поддерживает ли уже текущий движок требуемое поведение.

**Правила одной модели нельзя переносить на другую только потому, что они относятся к одной категории мебели.**

Нельзя предполагать, что:

- у стола четыре ножки;
- у стола вообще обязательно есть ножки;
- все столы изменяют и длину, и ширину;
- вся мебель изменяется по одинаковым осям;
- круглый стол ведёт себя как прямоугольный;
- опоры должны масштабироваться вместе со столешницей;
- физический механизм раздвижения с референса нужно обязательно воспроизводить буквально.

## 3. Пространственная система координат

Пространственные оси ассета стандартизируются отдельно от смысловых названий вроде `length`, `width`, `depth` и `diameter`.

Стандарт проекта:

```text
X = горизонтально слева ↔ направо
Y = вертикально вверх
Z = горизонтально спереди ↔ назад
```

Для мебели с однозначно определяемой передней стороной предпочтительное направление front:

```text
+Z
```

Если требуется другое направление, оно обязательно указывается в паспорте модели.

Семантические размеры сопоставляются осям отдельно для каждой модели.

Примеры:

```text
Прямоугольный стол:
length -> X
width  -> Z
height -> Y

Шкаф:
width  -> X
depth  -> Z
height -> Y

Круглый стол:
diameter -> X + Z
height   -> Y
```

Нельзя глобально утверждать, что «width всегда X» или «length всегда X».  
Источником истины является конфигурация конкретной модели.

## 4. Единицы и реальный физический масштаб

В техническом описании размеры могут задаваться в миллиметрах:

```text
1200 × 700 × 750 mm
```

Экспортированный GLB использует реальный метрический масштаб:

```text
1 Three.js unit = 1 meter
1200 mm = 1.2
```

**Финальные внешние размеры экспортированной модели**, после всех необходимых modifiers и bevel, должны соответствовать паспорту.

Номинальный размер 1200 mm не должен незаметно превратиться в 1214 mm из-за bevel или другого modifier.

`dimensions.*.base` всегда соответствует исходному GLB и служит базой resize.
Если начальная настройка приложения отличается, задаётся отдельный `defaultValue`
в пределах min/max и на сетке step. Он применяется к новой конфигурации и сбросу;
сохранённые допустимые значения имеют приоритет. Геометрия обязана получить этот
размер через обычный контроллер, а не только отобразить его в поле ввода.

## 5. Root и контакт с полом

Для обычной напольной мебели предпочтительный стандарт:

```text
root position = (0, 0, 0)
floor/contact plane = Y = 0
```

Ассет логически располагается около `X = 0` и `Z = 0`, если предполагаемый resize anchor не требует другого решения.

Для настенной и специальной мебели root выбирается в соответствии со способом установки и описывается в паспорте.

Положение root должно оставаться стабильным между экспортами.

## 6. Иерархия GLB

У каждого ассета должен быть один понятный root.

Примеры:

```text
Table_RoundOak
Wardrobe_ThreeDoor
Dresser_Classic
```

Внутри root геометрия разделяется по **runtime-поведению и реальной конструкции**, а не только по удобству моделирования в Blender.

Возможные nodes:

```text
TableTop
Top_LeftCap
Top_Center
Top_RightCap
Leg_01
Leg_02
Pedestal_Left
Pedestal_Right
CentralSupport
Frame_Left
Frame_Right
CrossRail
Apron_Front
Door_Left
Door_Right
Shelf_01
Drawer_01
Handle_01
```

Управляемым node может быть как Mesh, так и Group.

Group предпочтителен, когда целая реальная сборка должна перемещаться как одно целое, а её внутренняя геометрия должна оставаться неизменной.

### Критическое правило иерархии

Геометрия, которая должна вести себя по-разному в конфигураторе, не объединяется в один неуправляемый объект.

А объект, который должен оставаться fixed, не должен быть descendant объекта, который будет масштабироваться.

Всегда учитывается наследование transforms в Three.js:

```text
масштабируется parent
        ↓
все descendants наследуют scale
```

Поэтому `Scale`-target не должен содержать descendants, которые должны сохранять собственный размер или перемещаться независимо.

## 7. Имена — часть runtime API

Имена, используемые конфигуратором, являются частью контракта ассета.

Все имена управляемых nodes должны быть:

- стабильными;
- осмысленными;
- английскими;
- ASCII-compatible;
- единообразными по регистру;
- по возможности без пробелов;
- глобально уникальными внутри GLB.

Нельзя передавать runtime-управляемые nodes с именами:

```text
Cube
Cube.001
Object.023
Plane.004
```

Примеры допустимых API-имён:

```text
TableTop
Leg_01
Leg_02
Pedestal_Left
Door_Left
Drawer_01
Top_LeftCap
Top_Center
Top_RightCap
```

В текущем проекте управляемые объекты находятся по имени, поэтому дублирующиеся runtime-имена внутри одного GLB запрещены.

Переименование управляемого node между экспортами считается breaking API change, если соответствующий TypeScript-конфиг не обновлён намеренно.

## 8. Локальные transforms и управляемые оси

Runtime-управляемые объекты должны находиться в предсказуемой локальной системе координат.

Без технической необходимости следует избегать:

- случайно повернутых промежуточных parent-групп;
- скрытого non-uniform parent scale;
- отрицательного parent scale;
- цепочек transforms, делающих локальные оси управляемого node непредсказуемыми;
- случайных transforms, оставшихся от истории моделирования.

Предпочтительные значения там, где они совместимы с нужными pivots:

```text
root rotation = 0
root scale    = 1

controlled group rotation = 0
controlled group scale    = 1
```

Для наклонного конструктивного элемента допустим собственный rotation, если его **локальная продольная ось выбрана намеренно и задокументирована**.

Пример:

Диагональная распорка может иметь local `Y` вдоль своей физической длины, хотя параметр мебели `length` связан с глобальной осью X.

Это обязательно указывается в паспорте/конфиге.

## 9. Контракт Pivot / Origin

Pivot проектируется под runtime-поведение.

Примеры:

- дверца -> pivot на оси петель;
- выдвижной ящик -> origin, удобный для линейного перемещения;
- вращающийся элемент -> pivot на оси вращения;
- перемещаемая опорная сборка -> предсказуемая точка привязки;
- масштабируемая центральная секция -> pivot, соответствующий resize anchor;
- root -> логическая точка позиционирования всей мебели.

Origin нельзя оставлять случайным только потому, что так было удобно во время моделирования.

## 10. Resize anchors

У каждого конфигурируемого физического размера должен быть явно указан resize anchor.

Допустимые описательные значения:

```text
center
min-edge
max-edge
custom
```

Пример:

```text
dimension: length
model axis: X
anchor: center
```

Centered resize означает симметричный рост мебели в обе стороны.

Edge-anchored resize означает, что одна логическая сторона остаётся на месте.

Если модель должна изменяться только в одну сторону, это необходимо знать **до начала моделирования**, потому что это влияет на:

- pivots;
- соединение фасадов с коробами ящиков и зазоры открытых дверей по разделу 39;
- перемещение опор;
- сегментацию геометрии;
- UV offset;
- центрирование текстуры.

Текущий проект лучше всего поддерживает centered resize.  
Одностороннее поведение должно быть явно отмечено, если для него требуется расширение движка.

### 10.1 Готовность модели к изменению высоты

Для каждой production-модели стола в паспорте явно указывается один из статусов:

```text
height-configurable — высота доступна пользователю сейчас
height-ready        — структура подготовлена, но UI-параметр пока не включён
height-fixed        — текущая структура не предполагает изменение высоты
```

Статус `height-ready` или `height-configurable` требует:

- отдельных semantic nodes для вертикальных опор или их растягиваемых сегментов;
- задокументированной local longitudinal axis каждой опоры;
- известной физической `baseLength` вертикального сегмента;
- pivot и hierarchy, позволяющих сохранить контакт с полом;
- отдельного управляемого node столешницы и других деталей, которые должны подниматься;
- сохранения поперечного сечения опор при изменении высоты;
- явного описания floor anchor и верхней точки крепления.

Для простой вертикальной опоры текущий generic runtime может реализовать изменение высоты комбинацией существующих правил:

```text
vertical support:
  height -> Stretch segment по local longitudinal axis
  height -> Delta move с factor 0.5 для сохранения нижнего края на полу

tabletop / upper assembly:
  height -> Delta move с factor 1
```

Точные коэффициенты зависят от pivot и конструкции конкретной модели. Они не должны копироваться между моделями без проверки.

Если высота меняет угол наклонной опоры, соединяет две движущиеся точки или требует телескопической/вариантной конструкции, модель может потребовать `Fit between anchors`, visibility/variant или другое расширение движка.

Physical dimension `height` не обязана автоматически соответствовать local `Y`: semantic dimension и local axis по-прежнему задаются декларативно.

### 10.2 Готовность столешницы к изменению толщины

Если текущая или будущая конфигурация предполагает изменение толщины столешницы, паспорт обязан определить:

- semantic dimension, например `topThickness`;
- base/min/max/step;
- local scale axis столешницы;
- базовую физическую толщину;
- неподвижную опорную плоскость толщины;
- какие связанные детали должны перемещаться вслед за изменившейся поверхностью;
- UV-поведение верхней, нижней и торцевых поверхностей.

Допустимые описательные anchors толщины:

```text
bottom-surface — нижняя плоскость остаётся неподвижной, толщина растёт вверх
top-surface    — верхняя плоскость остаётся неподвижной, толщина растёт вниз
center         — толщина изменяется симметрично относительно центра
custom         — поведение полностью описывается в паспорте
```

Anchor толщины не выбирается generic controller автоматически. Он является частью контракта конкретной модели и реализуется подходящими декларативными resize rules.

## 11. Типы runtime-поведения

Каждая управляемая часть получает одно или несколько явно определённых runtime-поведений.

### 11.1 Fixed

Деталь сохраняет размер и положение.

Resize-rule не требуется.

Примеры:

- центральный pedestal, когда растёт только столешница;
- декоративная вставка;
- фиксированная опорная плита.

### 11.2 Scale

Деталь физически изменяет размер по задокументированной **локальной** оси.

Примеры:

```text
TableTop:
length -> local X

RoundTop:
diameter -> local X
diameter -> local Z
```

Scale допустим только тогда, когда растягивание target физически и визуально корректно.

Нельзя использовать Scale, если это:

- изменяет толщину ножки;
- увеличивает винт;
- искажает декоративный профиль;
- меняет радиус скругления, который должен оставаться постоянным;
- делает конструктивную трубу толще.

### 11.3 Edge-anchor move

Деталь сохраняет собственные размеры и перемещается вместе с изменяемым внешним краем, сохраняя постоянный отступ.

Типичные случаи:

- четыре ножки стола, перемещающиеся к новым углам;
- две опорные сборки, расходящиеся при увеличении длины;
- боковые рамы, смещающиеся наружу.

### 11.4 Delta move / spread

Деталь сохраняет размеры, но перемещается на величину, вычисляемую относительно **изменения конфигурируемого размера**, а не напрямую относительно внешнего края.

Концептуально:

```text
newPosition =
basePosition
+
dimensionDelta * factor
```

Типичные случаи:

- опора, визуально являющаяся одной в базовом состоянии, но созданная как две независимые половины, которые расходятся при увеличении стола;
- внутренние опоры, расходящиеся с пользовательским коэффициентом;
- компоненты, которые должны двигаться, но не привязаны непосредственно к краю столешницы.

Текущий runtime поддерживает это поведение generic-правилом `delta-move`.

Фактический расчёт текущего движка:

```text
dimensionDelta = currentDimension - baseDimension
newPositionOnAxis = capturedBasePositionOnAxis + dimensionDelta * factor
```

Знак `factor` задаёт направление. Позиция всегда вычисляется от захваченного base state, а не от текущей позиции, поэтому последовательные изменения размеров не накапливают drift.

Ось `axis` относится к локальной системе parent управляемого объекта. Один rule может содержать несколько targets с независимыми коэффициентами.

### 11.5 Stretch segment

Специальный сегмент растягивается только по своей продольной оси, сохраняя неизменным поперечное сечение.

Типичные случаи:

- направляющие;
- царги;
- центральные полосы;
- балки каркаса.

Сегмент должен быть смоделирован так, чтобы его local stretch axis совпадала с предполагаемым направлением runtime-растяжения.

Текущий runtime поддерживает это поведение generic-правилом `stretch-segment`.

Фактический расчёт текущего движка:

```text
targetLength = baseLength + (currentDimension - baseDimension) * factor
newScaleOnAxis = capturedBaseScaleOnAxis * (targetLength / baseLength)
```

`factor` по умолчанию равен `1`. `baseLength` должен быть положительным и соответствовать физической длине сегмента при base dimension.

Изменяется только указанная local axis. Две остальные компоненты scale, rotation и поперечное сечение сохраняются. Поэтому intentionally rotated элемент остаётся допустимым, если его продольная local axis задокументирована правильно.

### 11.6 Fit between anchors

Конструктивный элемент должен постоянно соединять две перемещающиеся точки крепления.

Runtime может изменять:

- position;
- rotation;
- продольный scale.

Типичные случаи:

- диагональные распорки;
- V-образные элементы;
- наклонные растяжки.

Это поведение **не равно обычному Scale по размеру мебели**.

Если оно требуется, модель помечается как `Requires engine extension`, пока runtime не поддерживает такой generic-rule.

### 11.7 Visibility / variant

Node или Group может появляться/исчезать в зависимости от состояния конфигурации.

Типичные случаи:

- центральная заполняющая секция, видимая только после начала расширения;
- альтернативная фурнитура;
- дополнительные полки;
- декоративные элементы варианта.

Предпочтительно заранее создавать семантические nodes, а не генерировать произвольную Blender-геометрию в runtime.

### 11.8 Reconfigure / regenerate

Конфигурация требует настоящего изменения топологии или количества деталей.

Примеры:

- переменное число полок;
- динамически повторяемые рейки;
- замена одной конструктивной схемы на другую;
- генерируемая геометрия.

В модульном конструкторе столов уже реализована генерация выпуклой столешницы
по отдельному контракту [table-module-standard-v1.md](table-module-standard-v1.md).
Это не добавляет произвольную regeneration-rule в FurnitureController. Для других
случаев неподдерживаемой генерации паспорт обязательно должен содержать:

```text
Requires engine extension
```

Модель, чьё основное поведение зависит от неподдерживаемой regeneration-логики, не считается полностью plug-and-play для текущего движка.

## 12. Совместимость с текущим конфигуратором

На момент этой версии стандарта проект уже имеет generic model registry и config-driven dimensions.

Базовый runtime уже поддерживает:

```text
Fixed
Scale
Edge-anchor move
Delta move / spread
Stretch segment
multi-axis dimension mapping
centered texture repeat/offset compensation
declarative material slots
runtime finish replacement
persistent dimensions and material selection per model
configuration links with schema validation
```

Фактическая форма поддерживаемых resize rules в `FurnitureDefinition`:

```ts
type ScaleResizeRule = {
  type: 'scale'
  target: string
  dimension: string
  axis: 'x' | 'y' | 'z'
}

type EdgeAnchorResizeRule = {
  type: 'edge-anchor'
  targets: readonly string[]
  dimension: string
  axis: 'x' | 'y' | 'z'
  center?: number
}

type DeltaMoveResizeRule = {
  type: 'delta-move'
  targets: readonly {
    target: string
    factor: number
  }[]
  dimension: string
  axis: 'x' | 'y' | 'z'
}

type StretchSegmentResizeRule = {
  type: 'stretch-segment'
  target: string
  dimension: string
  axis: 'x' | 'y' | 'z'
  baseLength: number
  factor?: number
}
```

Physical dimension и local/model axis не выводятся друг из друга и всегда задаются отдельно.

Примеры production-моделей, проверяющих этот контракт (весь актуальный каталог — в README.md и furnitureRegistry.ts):

```text
table-01 / First Table
  base: 1.20 × 0.60 m
  max:  2.00 × 1.00 m
  behaviors: Scale + Edge-anchor move

table-02-u-frame / U-Frame Table
  base: 0.95 × 0.55 × 0.75 m
  max:  1.65 × 0.80 × 0.75 m
  behaviors:
    Scale
    Delta move / spread
    Edge-anchor move
    Stretch segment
```

`table-02-u-frame` использует две U-образные рамы: рамы расходятся по длине, стойки перемещаются по ширине без изменения профиля, нижние поперечины растягиваются только по local Z.

### Текущий статус material replacement

Общий material catalog, generic material controller, пользовательские selectors, локальное сохранение размеров/материалов и ссылки на конфигурации уже реализованы.

Каждая модель декларативно описывает заменяемые группы через `materialSlots`:

```ts
type FurnitureMaterialSlotConfig = {
  label: string
  targets: readonly string[]
  defaultFinish: string
  allowedFinishes: readonly string[]
}

type FurnitureDefinition = {
  // dimensions, resizeRules, textureAxes и другие поля
  materialSlots?: Readonly<
    Record<
      string,
      FurnitureMaterialSlotConfig
    >
  >
}
```

`targets` содержит точные semantic `material.name` из GLB. Один slot может одновременно заменять несколько совместимых материалов, например top/bottom/edge surfaces столешницы. Один semantic material target не должен принадлежать двум slots одной модели.

`defaultFinish` обязан входить в `allowedFinishes`. Все finish IDs должны существовать в общем material registry; generic controller не содержит названий моделей, столов, ножек или специальных GLB nodes.

Текущий общий каталог содержит texture-based finishes:

```text
oak-natural
walnut-natural
pine-coated
ash-natural
concrete-light
marble-cream
oak-grey
oak-silver
oak-black
marble-white-gold
marble-black-gold
marble-duo-gold
terrazzo-neutral
```

и procedural powder-coated metal finishes:

```text
metal-black-matte
metal-white-matte
metal-anthracite
```

Texture finishes используют Base Color, Roughness и Normal GL. Base Color загружается как sRGB, data maps — без color space; включены repeat wrapping, mipmaps и ограниченная renderer anisotropy. Для окрашенного металла используется низкий `metalness`, потому что видимая поверхность является полимерным покрытием, а не открытым металлом.

После runtime-замены material controller сообщает furniture controller о новых текстурах. Текущие dimensions применяются повторно от base state, поэтому texture repeat/offset compensation сохраняется и материал не начинает растягиваться после последовательности resize → finish switch → resize.

Размеры и finishes хранятся отдельно для каждой модели в localStorage и могут
передаваться по ссылке. Модульная сборка имеет собственное состояние, проверку
совместимости и ссылки. Пользовательская загрузка материалов и swatch previews
пока не поддерживаются.

Архитектура **не предполагает четыре ножки** или какую-либо фиксированную структуру мебели.

Следующие типы поведения являются допустимыми целями для ассетов, но перед интеграцией могут потребовать добавления новых generic-rule в движок:

```text
Fit between anchors
conditional visibility / variants
shape-preserving segmented resize helpers
dynamic part count
arbitrary geometry regeneration outside the tabletop module factory
morph-target driven behavior
```

Стандарт намеренно фиксирует их заранее, чтобы модели могли проектироваться корректно до реализации соответствующей runtime-логики.

Когда движок получает новую возможность, обновляется этот раздел совместимости, но фундаментальный контракт ассета не меняется.

## 13. Типовые конструктивные паттерны мебели

Это примеры, а не обязательные шаблоны.

### Pattern A — четыре, две или любое количество периферийных ножек

Количество ножек не имеет значения для движка.

Каждая перемещаемая ножка или сборка ножек — отдельный семантический Node/Group.

Типичное поведение:

```text
top -> Scale
legs/support groups -> Edge-anchor move
```

Если изменяются и длина, и ширина, каждая опора может получать правила перемещения по обеим соответствующим осям.

### Pattern B — одна центральная опора

Типичное поведение:

```text
top -> Scale
pedestal -> Fixed
```

Для круглой столешницы возможно:

```text
diameter -> X + Z
```

Никакой логики «количества ножек» не требуется.

### Pattern C — две опорные сборки

Типичное поведение:

```text
top -> Scale или segmented resize
left support  -> Move
right support -> Move
```

Две опоры обычно расходятся, сохраняя собственные размеры.

### Pattern D — одна опора, которая визуально разделяется на две

Если конфигуратор должен показывать разделение, нельзя моделировать такую опору одним неразделимым Mesh.

Предпочтительная структура:

```text
Pedestal_LeftPart
Pedestal_RightPart
```

В базовом состоянии они расположены так, чтобы визуально образовывать одну опору.

При увеличении длины runtime раздвигает их.

Это позволяет не генерировать топологию в runtime и делает поведение детерминированным.

### Pattern E — U-frame / боковые рамы

Каждая реальная сборка моделируется согласно своему поведению.

Возможная структура:

```text
Frame_Left
Frame_Right
Rail_Front
Rail_Back
CrossRail
```

Боковые рамы могут перемещаться.  
Продольные rails могут растягиваться только по своей локальной продольной оси.

Нельзя масштабировать всю визуально сварную раму целиком, если при этом меняется толщина профиля или ножек.

### Pattern F — наклонные / V / Y-образные опоры

Если опорная сборка просто перемещается как одно жёсткое целое, создаётся Group и перемещается группа.

Если наклонный элемент должен менять длину или угол между двумя перемещающимися точками крепления, сборка разделяется соответствующим образом, а элемент получает `Fit between anchors` или другой специализированный rule.

Нельзя решать задачу произвольным non-uniform scale, который изменяет толщину материала.

### Pattern G — шкаф / комод / тумба

Возможное поведение:

```text
side panels -> Move или Fixed
center panel -> Stretch
shelves -> Stretch или Reconfigure
doors -> Move / Scale / hinge animation
drawers -> Move
handles -> Move
```

Используется тот же словарь runtime-поведений; проект не является table-specific.

## 14. Shape-preserving resize — сохранение формы при изменении размеров

Обычный uniform/non-uniform scaling недопустим, когда внешний профиль должен сохранять фиксированную геометрию.

Важные примеры:

- круглая столешница должна становиться **капсулой/stadium**, а не эллипсом;
- углы rounded rectangle должны сохранять радиус;
- декоративные торцы;
- формованные или резные окончания;
- изогнутые царги.

### Круг -> эллипс

Если требуемый результат действительно является эллипсом, масштабирование круглой столешницы по одной оси может быть правильным.

### Круг -> капсула / стол с полукруглыми концами

Если требуемая форма должна сохранять фиксированные полукруглые торцы, а увеличивается только прямая средняя часть, **нельзя масштабировать весь круг по одной оси**.

Предпочтительная constructor-ready структура:

```text
Top_LeftCap     -> Fixed shape, Move
Top_Center      -> Stretch segment
Top_RightCap    -> Fixed shape, Move
```

Для точного состояния полностью круглого стола центральному сегменту может понадобиться visibility/variant rule либо специально спроектированное перекрытие.

### Rounded rectangle с изменением двух размеров

Если меняются и длина, и ширина, а радиус углов должен оставаться постоянным, возможна segmented / 9-slice структура:

```text
4 фиксированных угловых региона
4 edge-региона, растягивающихся по одной оси
1 центральный регион, растягивающийся по двум осям
```

Такое усложнение используется только тогда, когда оно действительно нужно визуально.

В паспорте обязательно указывается, допускается ли обычный scale или требуется profile-preserving resize.

## 15. Физический механизм товара и его представление в конфигураторе

Конфигуратор не обязан воспроизводить каждый скрытый физический механизм реального изделия.

Например, если реальный раздвижной стол увеличивается отдельной вставной доской, наш конфигуратор может отображать непрерывно изменяемую столешницу **если именно такое поведение согласовано для проекта**.

Но видимые движения опор, которые конфигуратор должен показывать, например:

- опоры расходятся;
- одна опора визуально разделяется на две;
- боковые рамы разъезжаются;
- центральная база остаётся fixed, а столешница увеличивается;

обязательно должны быть отражены в GLB hierarchy и паспорте модели.

Референс является источником информации о конструкции и внешнем виде, но не единственным источником runtime-поведения.

## 16. Качество геометрии

Ассет должен выглядеть правдоподобно и подходить для real-time WebGL.

Базовые требования:

- отсутствие лишних полигонов;
- отсутствие дублирующихся coplanar faces;
- отсутствие скрытой внутренней геометрии без функциональной или визуальной причины;
- корректные normals;
- отсутствие явных shading-артефактов;
- разумное количество subdivision/detail;
- корректное smoothing;
- отсутствие случайной zero-area geometry.

Не объединять объекты только ради уменьшения их количества, если это уничтожает необходимое runtime-управление.

---

## 17. Реалистичные кромки и bevel

Видимые производственные кромки обычно должны иметь небольшой реалистичный bevel.

Не использовать математически идеально острые края там, где реальная мебель имела бы обработку, ламинат, окраску или скругление.

Типичный bevel мебели может быть около 1–2 mm, но это **не универсальное значение**.

Bevel не должен:

- незаметно изменять внешние габариты;
- ломать предполагаемое resize-поведение;
- создавать чрезмерное количество геометрии;
- искажать профиль с фиксированным радиусом.

## 18. UV — часть runtime-контракта

UV проектируется с учётом будущего изменения размеров.

Материал не должен становиться «резиновым» при изменении размера.

Для каждой конфигурируемой поверхности определяется:

- physical dimension;
- model axis;
- texture axis;
- resize anchor;
- какая UV-ось меняет tiling;
- какая UV-ось остаётся неизменной;
- должно ли сохраняться центрирование текстуры.

Пример для прямоугольной столешницы:

```text
Top / Bottom:
length -> texture U
width  -> texture V

Long edge:
length -> texture U

Short edge:
width -> texture U
```

Этот пример не является универсальным.

### 18.1 Обязательное semantic-разделение столешницы

Для каждой production-модели стола поверхности столешницы разделяются по своему UV-поведению и роли в runtime material replacement.

Прямоугольная столешница должна иметь как минимум отдельные semantic material surfaces:

```text
Top
Bottom
Edge_Long
Edge_Short
```

Фактические стабильные `material.name` могут уточнять назначение, например:

```text
Top_Surface
Bottom_Surface
Top_Edge_Long
Top_Edge_Short
```

Для скруглённых, фигурных или сегментированных столешниц дополнительно выделяются несовместимые поверхности, например:

```text
Top_Edge_Corner
Top_Center
Top_LeftCap
Top_RightCap
```

Для круглой столешницы вместо long/short edge используется отдельная semantic perimeter edge surface. Названия зависят от геометрии, но верх, низ и торцевая поверхность не объединяются в один неразличимый material target.

Разделение material surfaces не требует автоматически создавать несколько Mesh. Один Mesh может использовать несколько material indices, если его геометрия должна изменяться как единый объект. Отдельные Nodes/Groups требуются только тогда, когда части имеют разное resize-поведение.

Все поверхности одной столешницы могут входить в один пользовательский material slot:

```text
primaryTop:
  targets:
    - Top_Surface
    - Bottom_Surface
    - Top_Edge_Long
    - Top_Edge_Short
    - Top_Edge_Corner
```

Пользователь при этом выбирает один finish для всей столешницы, а runtime получает возможность независимо компенсировать texture repeat/offset для каждой поверхности.

Запрещено использовать один общий material target для верхней, нижней, длинных и коротких торцевых поверхностей, если их physical dimension -> texture axis mapping различается. Это правило действует даже тогда, когда preview material визуально скрывает проблему при base dimensions.

Паспорт и integration test должны перечислять все semantic material surfaces столешницы и проверять сохранение физического масштаба текстуры после base → intermediate → max → base resize.

## 19. Физический масштаб текстуры должен сохраняться

При увеличении физической поверхности визуальный масштаб дерева, камня, ткани или другого материала должен оставаться приблизительно постоянным.

Нельзя допускать:

- растягивания древесного рисунка;
- огромного увеличения сучков;
- увеличения деталей normal map вместе с мебелью;
- движения текстуры по оси, физический размер которой не изменялся.

Three.js может менять `texture.repeat` / `texture.offset` в runtime.

GLB и UV должны быть совместимы с таким поведением.

Для centered resize tiling должен оставаться визуально центрированным.

Для одностороннего resize требуемый UV-anchor указывается отдельно.

### 19.1. Сегментированные панели — affine UV bindings (v2.6)

Для панелей с фиксированной толщиной и кромками поддерживается общее поле
`FurnitureDefinition.textureTransforms[semanticMaterial]` с независимыми
`u` / `v`. Binding содержит `dimension`, `baseLength`, `stretchFactor`,
`translationFactor`, `anchor`, `uvUnitsPerMeter`. Длины задаются в метрах;
`anchor` — в исходных UV-единицах. Контракт привязывается к длине конкретного
сегмента, а не ко всему габариту изделия.

При `delta = dimension - baseDimension`:

```text
factor = (baseLength + delta * stretchFactor) / baseLength
repeat = initialRepeat * factor
offset = initialOffset + initialRepeat *
         (anchor * (1 - factor) + delta * translationFactor * uvUnitsPerMeter)
```

Эти преобразования применяются ко всем картам материала, включая normal и
roughness, и пересчитываются от исходного состояния. Фиксированная кромка может
иметь `stretchFactor = 0`, но ненулевой `translationFactor`: её UV-фаза должна
следовать за перемещением, иначе на стыке появится шов. `textureAxes` остаётся
для существующих моделей; оба контракта на одном semantic material запрещены.

Приёмка проверяет UV против физической длины поверхности и дуг скругления
на реальном GLB при min / intermediate / max / return и после смены finish.
Направление волокон всех PBR-карт должно соответствовать контракту панели;
нельзя поворачивать только цветовую карту или менять общую текстуру ради
одной модели.

Пример production-подключения — `src/three/models/wardrobe-*/runtime.ts`.
Лёгкий `catalog.ts` описывает UI, а `loadRuntime()` загружает полные правила
и targets. До создания controller нужно дождаться runtime definition.
`displayUnit: 'mm'` сохраняет точность шага 1 мм в UI.
Справочник интеграции: [wardrobes-v1.md](wardrobes-v1.md).

## 20. UV для изогнутых и цилиндрических поверхностей

Изогнутые ассеты, например:

- цилиндрические pedestal;
- рифлёные колонны;
- круглые царги;
- изогнутые ножки;

требуют осознанного расположения UV seam и постоянной UV density.

Если изменяется сама окружность, в паспорте указывается, как должен вести себя texture tiling.

Декоративные рейки/рифление могут быть геометрией или material-detail, но выбранный способ должен оставаться устойчивым при планируемом resize.

---

## 21. Material names — часть API

Runtime-имена материалов должны быть стабильными и смысловыми.

Использовать семантические slot names, например:

```text
Wood_Top
Wood_Bottom
Wood_Edge_Long
Wood_Edge_Short
Wood_Primary
Metal_Frame
Fabric_Seat
Glass_Panel
Stone_Top
```

Нельзя называть заменяемый slot постоянным названием finish вроде `Oak`, если пользователь позже сможет выбрать walnut или pine.

Конфигуратор использует экспортированное `material.name`.

Поверхности с несовместимым UV-поведением не должны иметь одно material name только ради удобства.

Если несколько поверхностей используют одно имя материала, их runtime texture behavior должно быть совместимо.

---

## 22. Заменяемые материалы

Геометрия не должна быть необратимо привязана к одному finish.

Один совместимый asset должен позволять применять, например:

```text
Oak
Walnut
Pine
```

без переделки геометрии.

GLB может содержать корректный preview/default material, но production-выбор finish должен контролироваться системой материалов Three.js.

Preview material не должен зависеть от отсутствующих абсолютных путей Blender.

---

## 23. PBR conventions

Предпочтительный базовый набор карт:

- Base Color / Albedo;
- Roughness;
- Normal.

Дополнительно при необходимости:

- Ambient Occlusion;
- Metalness;
- другие карты, если они физически оправданы.

Для этого pipeline по умолчанию используется **OpenGL normal-map convention**.

Нельзя подключать DirectX normal map в OpenGL workflow без преобразования.

Все карты одного finish должны использовать совместимые UV и одинаковый физический масштаб.

Визуально золотой рисунок, пигмент, печать или декоративная прожилка покрытия сами по себе не являются металлом. Для такого finish золотой цвет хранится в Base Color, а `metalness` остаётся около `0`. Металлический response используется только для реально открытого металла, металлической фольги или физически подтверждённого металлического слоя.

---

## 24. Направление материала

Направленные материалы должны соответствовать реальной логике производства.

Для дерева:

- направление волокон должно соответствовать конструкции;
- связанные конструктивные детали не должны случайно менять направление волокон;
- разное направление допустимо, когда это соответствует реальному изготовлению.

То же правило относится к ткани, brushed metal, направленному рисунку камня и другим материалам.

---

## 25. Scene environment не является частью furniture asset

В обычный production GLB не экспортируются:

```text
Blender Camera
lights
test floor
HDRI
environment
scene background
reflection setup
tone-mapping setup
temporary helper objects
reference images
modeling guides
```

Эти элементы принадлежат общей Three.js scene/runtime.

Проект намеренно хранит presentation-слой централизованно, чтобы улучшения:

- света;
- пола;
- теней;
- HDRI/environment;
- reflections;
- tone mapping;
- camera defaults;
- texture filtering / anisotropy;

автоматически улучшали **все модели сразу**.

Удачные сценовые решения из внешних конфигураторов, например референса Vankov, реализуются в общей scene/runtime, а не копируются в каждый GLB.

---

## 26. Артефакты фильтрации текстур — runtime-задача

Муар, shimmering или дугообразные узоры, которые появляются только при определённых углах камеры, часто связаны с texture sampling, mipmaps, normal-detail и anisotropic filtering.

Не следует переделывать геометрию мебели только ради скрытия такого runtime rendering artifact, если не доказано, что ошибка находится именно в ассете.

Общий Three.js material/runtime layer должен управлять:

- mipmaps;
- min/mag filtering;
- anisotropy;
- renderer/material settings.

---

## 27. Чистые transforms

Перед финальным экспортом transforms должны быть чистыми и осмысленными везде, где их применение не ломает нужные pivots или hierarchy.

Избегать случайных значений вроде:

```text
Scale X = 0.0137
Rotation Z = 89.734°
```

если они появились только из истории моделирования.

Осмысленные rotations наклонных деталей допустимы и должны соответствовать задокументированному local-axis behavior.

Отрицательный scale для production controlled nodes следует избегать.

---

## 28. Содержимое экспорта

Production GLB содержит только то, что относится к ассету:

- semantic nodes/groups;
- render geometry;
- необходимые materials;
- необходимые textures, если они по дизайну встраиваются;
- намеренно поддерживаемые animation/morph data, если они явно нужны.

Временный Blender scene setup в GLB не попадает.

---

## 29. GLB не является конфигуратором

Не нужно пытаться зашить весь product configurator внутрь GLB.

Разделение ответственности:

### GLB

Предоставляет:

- geometry;
- semantic hierarchy;
- stable names;
- pivots;
- local axes;
- UV;
- material slots;
- physical scale.

### TypeScript / Three.js configurator

Управляет:

- selected model;
- dimensions;
- движением частей;
- resize rules;
- заменой материалов;
- texture repeat/offset;
- состоянием конфигурации;
- URL/localStorage state;
- runtime variants;
- общей scene/environment.

---

## 30. Web-ready без преждевременной разрушительной оптимизации

Ассеты должны быть разумными для браузерного rendering, но нельзя разрушать semantic structure только ради уменьшения размера файла.

Не включать автоматически:

```text
Draco
Meshopt
KTX2
```

пока loader pipeline проекта явно не поддерживает соответствующие decoder/transcoder.

После добавления поддержки compression этот стандарт может быть обновлён.

Приоритеты оптимизации:

1. удалить действительно ненужную геометрию;
2. сохранить control hierarchy;
3. сохранить необходимое визуальное качество;
4. затем применять поддерживаемую compression.

---

## 31. Performance passport

Для каждого финального ассета желательно фиксировать:

- размер GLB;
- количество triangles;
- количество Mesh;
- количество materials;
- разрешения textures;
- необычно дорогие features.

Единого лимита triangles для любой мебели нет, но неожиданно тяжёлый asset должен иметь обоснование.

---

## 32. Проверка перед передачей

Перед передачей проверить:

- реальные финальные внешние размеры;
- положение root;
- floor contact на `Y = 0` для напольной мебели;
- front direction;
- hierarchy;
- глобальную уникальность controlled node names;
- стабильность material names;
- pivots;
- предполагаемые local axes;
- parent transforms;
- отсутствие fixed descendants внутри scale-target;
- normals и shading;
- bevel;
- UV;
- обязательное semantic-разделение верхней, нижней и торцевых поверхностей столешницы;
- направление материалов;
- совместимость с заменяемыми finishes;
- явно задокументированный height-readiness status;
- явно задокументированный thickness-readiness status и thickness anchor;
- отсутствие лишних объектов сцены;
- отсутствие неподдерживаемой compression;
- отсутствие случайных transforms.

Дополнительно:

1. экспортировать GLB;
2. открыть/реимпортировать его в чистой Blender-сцене;
3. убедиться, что structure, scale, materials и UV сохранились;
4. по возможности загрузить его в проект или небольшой Three.js validation harness.

---

## 33. Обязательный комплект исходников одной production-модели

Новая модель не передаётся как один случайный GLB. Рекомендуемая структура проекта:

```text
MODEL_PACKAGE_MANIFEST.md

public/models/<model-id>.glb

src/three/models/<model-folder>/
├── config.ts
└── <model-name>.test.ts

assets/source/<model-id>/
├── README.md
├── model-passport.md
├── validation-report.md
├── create_<model_id>.py
├── <model-id>.blend
├── references/
├── textures/
└── previews/
```

Для model-only Work-чата эта структура упаковывается в один ZIP с сохранением относительных путей от корня проекта.

Обязательны:

- production GLB;
- настоящий `FurnitureDefinition`/config;
- integration test реального production GLB;
- паспорт модели;
- validation report;
- исходные текстуры;
- переданные референсы;
- изображения как минимум base и max состояний;
- editable Blender source либо воспроизводимый Blender generation script.

`MODEL_PACKAGE_MANIFEST.md` должен содержать:

- список всех моделей внутри архива;
- список всех файлов архива;
- `modelId` и предлагаемое человекочитаемое label;
- base/min/max/step;
- использованные generic behaviors;
- material names и finish groups;
- результаты `npm test`, `npm run build` и glTF Validator;
- все допущения и ограничения;
- точную запись, которую центральный integration-чат должен добавить в registry.

Model package ZIP не должен содержать:

```text
.git/
node_modules/
dist/
Git bundle
полную копию проекта
изменённый FurnitureController
изменённый App.tsx
изменённый configurator state
изменённый furnitureRegistry.ts
```

Общие файлы проекта намеренно не кладутся в model package, чтобы архив одной параллельной задачи не перезаписал более свежую архитектуру другой задачи.

`.blend` является главным редактируемым source asset, а GLB — браузерным production asset.

Если среда Work-чата не содержит Blender, запрещено создавать фиктивный `.blend` или утверждать, что файл проверен в Blender. В таком случае чат должен:

1. честно зафиксировать ограничение;
2. предоставить детерминированный Blender Python script;
3. проверить синтаксис скрипта доступным способом;
4. дать точную команду запуска через Blender 4.x;
5. попросить пользователя создать `.blend` локально и затем выполнить финальную Blender-проверку.

Отсутствие Blender не освобождает от проверки production GLB в Three.js и glTF Validator.

---

## 34. Обязательная автоматическая проверка модели

Тестирование не ограничивается тем, что GLB визуально открылся.

Минимальный integration test production GLB должен проверять:

- успешную загрузку через `GLTFLoader`;
- наличие всех targets из config по точным именам;
- base dimensions контроллера;
- base transforms управляемых объектов;
- максимальные значения всех configurable dimensions;
- сохранение сечения fixed/moving деталей;
- изменение только разрешённых local axes;
- корректное движение положительных и отрицательных targets;
- texture repeat/offset compensation;
- независимое UV-поведение всех semantic surfaces столешницы;
- возврат точно к base state после серии изменений;
- сохранение floor contact и поперечного сечения опор при configurable height;
- сохранение выбранной опорной плоскости при configurable tabletop thickness;
- наличие ожидаемых semantic material names;
- наличие replaceable finish metadata, если она предусмотрена.

Для каждого законченного изменения выполняются:

```text
npm test
npm run build
```

Production GLB дополнительно проверяется Khronos glTF Validator. Целевой результат:

```text
Errors:   0
Warnings: 0
```

Информационные сообщения оцениваются отдельно и фиксируются, если они указывают на осознанный компромисс.

После автоматических проверок выполняется визуальный smoke-test:

- base state;
- max state;
- промежуточное состояние;
- возврат к base;
- переключение на другую зарегистрированную модель и обратно.

---

## 35. Workflow для Work-чата, создающего новую модель

### До изменений

Work-чат обязан:

1. проверить текущую ветку и `git status`;
2. убедиться, что исходная ветка содержит актуальный `main`;
3. создать отдельную feature-ветку;
4. прочитать этот стандарт полностью;
5. изучить реальные `FurnitureDefinition`, `FurnitureController`, loader/dispose, registry, state и существующие model configs;
6. выполнить baseline `npm test` и `npm run build`;
7. изучить все референсы и выписать неизвестные размеры.

### До моделирования

Сначала формируется краткий runtime-контракт:

```text
modelId
base/min/max/step
dimension mapping
resize anchors
node hierarchy
behavior каждого controlled node
local axes
material slots и finish groups
UV behavior
tabletop semantic surfaces
height-readiness status
thickness-readiness status и anchor
assumptions
runtime compatibility
```

Неизвестные производственные размеры нельзя выдавать за данные референса. Разумные визуальные допущения разрешены только с явной записью в паспорте.

Если модель требует неподдерживаемого поведения, Work-чат не должен незаметно имитировать его неправильным scale. Он останавливает интеграцию, помечает `Requires engine extension` и объясняет, какого generic rule не хватает.

### Реализация

Предпочтительный порядок:

```text
контракт
→ semantic hierarchy
→ geometry/materials/UV
→ проверка semantic surfaces столешницы
→ проверка height/thickness readiness
→ GLB validation
→ FurnitureDefinition
→ integration test
→ visual smoke-test
→ passport/source package
→ model package ZIP
```

Generic engine не должен получать:

- `if (modelId === ...)`;
- знания о столах, ножках или количестве опор;
- специальные node names конкретной модели;
- предположение `length = X` или `width = Z`;
- встроенные в `App.tsx` правила конкретного GLB.

Новая модель должна стремиться к схеме:

```text
GLB + FurnitureDefinition + tests + source package
```

без изменений generic controller. Расширение controller допустимо только отдельной согласованной задачей на новое универсальное поведение.

### Завершение

Work-чат обязан:

1. выполнить тесты и build;
2. проверить GLB валидатором;
3. показать base/max previews;
4. перечислить допущения и неподдерживаемые функции;
5. сделать логические commits;
6. оставить результат в feature-ветке;
7. не мержить `main` без явного подтверждения пользователя;
8. собрать `MODEL_PACKAGE_MANIFEST.md`;
9. предоставить один model package ZIP;
10. **не предоставлять Git bundle**, если задача была обозначена как model-only;
11. не предлагать пользователю распаковывать ZIP поверх рабочего проекта — архив предназначен для центрального integration-чата.

Для собственных runtime-проверок model-only чат может временно зарегистрировать модель в своей локальной ветке, но `furnitureRegistry.ts` и другие изменённые shared files не включаются в итоговый ZIP.

---

## 36. Параллельная разработка нескольких моделей

Несколько Work-чатов могут создавать модели параллельно, если соблюдаются границы интеграции.

Для каждой параллельной задачи необходимы:

- отдельная feature-ветка;
- уникальный `modelId`;
- уникальный путь GLB;
- уникальная source-папка;
- уникальная папка model config/tests;
- собственный паспорт и validation report.

Рекомендуемое именование:

```text
feat/model-table-03
feat/model-table-04
feat/furniture-models-batch-01
```

Нельзя двум чатам независимо изменять generic engine под свои модели. Если обе модели выявили одну и ту же отсутствующую возможность, создаётся отдельная engine-задача, после её merge model-ветки обновляются от нового `main`.

Model-only чаты не передают свои branches/bundles пользователю и не являются точкой интеграции. Они возвращают изолированные ZIP-пакеты новых моделей.

Перед началом следующей волны параллельных моделей участникам может передаваться свежий Git bundle или архив актуального `main` только как **входной snapshot для разработки и тестов**. Это не меняет формат результата: model-only чат возвращает ZIP.

Если один Work-чат создаёт сразу несколько моделей, они могут находиться в одной batch-ветке, но каждая модель всё равно должна иметь отдельные:

- GLB;
- config;
- integration test;
- паспорт;
- source package;
- validation result.

Материалы подготавливаются как semantic slots/finish groups. Model-only ветка декларативно предлагает `materialSlots`, используя существующие finish IDs общего каталога, но не добавляет собственный selector и не изменяет общую material system.

### Центральный integration flow

Безопасная последовательность:

1. model-only Work-чат возвращает ZIP;
2. пользователь не распаковывает ZIP в `<project-root>`;
3. пользователь передаёт ZIP центральному integration-чату;
4. integration-чат начинает с актуального `main` и отдельной integration-ветки;
5. integration-чат проверяет manifest и содержимое архива;
6. копирует только разрешённые model files;
7. обновляет актуальный `furnitureRegistry.ts`;
8. при необходимости адаптирует model config к уже изменившимся generic types, не добавляя model-specific логику;
9. выполняет общие tests, build, GLB validation и визуальную проверку переключения моделей;
10. при наличии репозитория делает интеграционные commits;
11. возвращает проверенный ZIP с относительными путями и командами отдельного коммита
    либо Git bundle готовой integration-ветки, если используется bundle workflow.

Именно проверенный интеграционный пакет становится источником файлов модели
для рабочего репозитория пользователя. Сырой model-only пакет этим результатом не является.

ZIP не пропадает сам по себе после импорта другого bundle, однако его распакованные файлы могут остаться untracked, не попасть в историю Git, столкнуться с совпадающими путями или потеряться при последующей очистке/переносе проекта. Поэтому ZIP не считается интегрированным, пока его содержимое не добавлено и не закоммичено центральным integration flow.

Если пользователь всё же вручную распаковал model package, он не должен продолжать импорт других веток до проверки `git status`. Содержимое необходимо либо сразу интегрировать и закоммитить в отдельной ветке, либо убрать из рабочей директории. Оставлять важные model files как untracked запрещено.

## 37. Сопроводительное сообщение для model-only Work-чата

В новый Work-чат вместе со стандартом, актуальным snapshot проекта и референсами можно отправить следующий текст:

```text
Мы параллельно развиваем проект Furniture 3D Configurator. Твоя зона ответственности — только создание новых constructor-ready мебельных моделей и их model packages.

Сначала полностью прочитай приложенный 3d-furniture-asset-standard.md и изучи реальный код переданного проекта. До моделирования сформируй runtime-контракт каждой модели и покажи мне краткий план. Не начинай реализацию до моего утверждения плана.

Используй только уже поддерживаемые generic behaviors текущего FurnitureController. Не изменяй generic engine, FurnitureController, App.tsx, configurator state, общую material system или архитектуру registry. Не добавляй if по modelId. Если модели не хватает runtime-возможности, остановись и укажи Requires engine extension.

Можешь временно зарегистрировать модель в своей локальной ветке для тестирования, но итоговый результат должен быть одним ZIP-пакетом, содержащим только новые model-specific файлы с путями от корня проекта:

- MODEL_PACKAGE_MANIFEST.md;
- public/models/<model-id>.glb;
- src/three/models/<model-folder>/config.ts;
- integration test production GLB;
- assets/source/<model-id>/ с README, паспортом, validation report, референсами, текстурами, previews и .blend либо воспроизводимым Blender script.

Не включай в ZIP .git, node_modules, dist, полную копию проекта, furnitureRegistry.ts или изменённые shared/generic files.

Обязательно проверь npm test, npm run build, production GLB через glTF Validator и визуально base/max состояния. Зафиксируй результаты и все допущения в manifest/паспорте.

Для каждой модели стола обязательно раздели верхнюю, нижнюю, длинные и короткие торцевые поверхности столешницы на отдельные semantic material targets; для круглой/фигурной формы используй эквивалентное разделение по UV-поведению. Они могут оставаться частями одного Mesh и входить в один пользовательский finish slot.

В паспорте обязательно укажи `height-configurable`, `height-ready` или `height-fixed`, а также аналогичный статус готовности столешницы к изменению толщины и выбранный thickness anchor, если такая настройка предусмотрена.

Не присылай Git bundle и не предлагай мне распаковывать ZIP поверх рабочего проекта. ZIP будет передан в отдельный центральный integration-чат, который подключит модели к актуальной принятой версии и вернёт проверенный интеграционный пакет.
```

## 38. Отдельные модули столов

Готовая модель и модуль — разные типы поставки. В дополнение к готовым GLB-столам
приложение поддерживает параметрическую столешницу и отдельный GLB основания.
Контракт, attachment nodes, формы, UV, высота, толщина, совместимость и формат
поставки описаны в [table-module-standard-v1.md](table-module-standard-v1.md).

При создании следующего основания передавайте оба стандарта. Модуль нельзя
подключать только по фотографии: нужно заранее определить плоскость крепления,
поддерживаемые формы, диапазоны столешницы, материал и правила изменения высоты.
Нельзя масштабировать основание целиком вслед за размерами столешницы.
Текущий контракт модулей v1.5 задаёт общий диапазон регулируемых оснований
64–84 см с шагом 1 см, включает четыре прямые ножки, U-рамы и V-основание,
отступы от срезанных углов и ограничение пропорций овальных столешниц.
Специализированная деформация прямых ножек сохраняет сечение и торцевые фаски;
она не расширяет автоматически resize-контракт готовых моделей.
Параметрическая столешница поддерживает четыре профиля: фаски 1/5 мм,
скругление R5 и мягкую кромку с полуэллиптическим сечением (заход не больше
10 мм) и непрерывным переходом текстуры с верхней плоскости. Кромка строится
внутрь контура, сохраняя габариты, толщину и плоскость крепления. Эта функция
не требует новых GLB; готовые импортированные столы сохраняют свои профили.
Для центральных оснований проверяется фактический контакт ядра с нижней
площадкой, включая скругления и фаски: одного пересечения bounding boxes мало.

Модели шкафов, начатые по v2.4, продолжают использовать прежний FurnitureDefinition
и проходят обычную интеграцию; модульный контракт столов к ним не применяется.

## 39. Соединения открывающихся фасадов

Закрытый вид недостаточен для приёмки шкафа или комода. Проверяется именно
экспортированный GLB с production resize и открыванием, а не только исходная сцена.

### Ящик

Фасад, короб, ручка, декор и подвижная часть направляющих должны находиться
в одной сборке. Корпус и неподвижные направляющие остаются вне неё.

Для текущей конструкции с накладным фасадом передние торцы обеих боковин,
дна и внутренняя передняя стенка короба доходят до задней плоскости фасада.
Номинальный воздушный зазор в этом соединении — **0 мм**. Это не зазор
между соседними фасадами и не боковой монтажный зазор направляющих:
те задаются отдельно и сохраняются.

В координатах модели с передней стороной `+Z`: `boxFront = facadeBack`.
При изменении глубины короб растёт до этой плоскости, задний отступ сохраняется.
Нельзя сдвигать весь короб вперёд вместе с задней стенкой или растягивать фасад
для маскировки щели. Если реальная конструкция использует кронштейны и отступ,
нужен отдельный контракт с размерами и геометрией соединителей.

Проверить фактические поверхности, включая bevel: пересечения bounding boxes
недостаточно. Для текущих стыков допускается численная погрешность **0,1 мм**.
Автопроверка должна измерять несколько точек на соединяемых поверхностях.

### Распашная дверь

Ось задаётся относительно кромки полотна у петель и монтажной стороны корпуса.
В текущей визуальной модели накладной двери ось проходит по **задней плоскости
фасада**, а не по его передней поверхности. Перенос оси не меняет закрытые
мировые координаты полотна, ручек и декора: локальные координаты детей
пересчитываются относительно нового pivot.

Это правило относится к принятому простому повороту вокруг Y. Для другого
типа петли или фасада допускается иная траектория, обоснованная конструкцией.
Вращение вокруг одной оси не является точной кинематикой четырёхзвенной петли;
упрощённую фурнитуру нужно обозначать в паспорте как приблизительную.

Сохранять предусмотренный закрытый зазор до корпуса (в текущих моделях 2–4 мм),
не добавляя к нему толщину фасада при открывании. Проверить боковой вид и
траекторию от 0° до конечного угла, включая промежуточные положения:
полотно не должно проходить сквозь боковины, перегородки, полки и крышку.

### Приёмка и воспроизводимость

- Закрыто, открыто наполовину, открыто полностью, возврат в закрытое положение.
- `base/min/max`, а также широкая неглубокая и узкая глубокая конфигурации.
- Изменение размеров при открытых фасадах и повторный возврат к `base`.
- Крупные боковые ракурсы стыка фасад–короб и петлевой кромки; общий вид спереди
  не заменяет эти проверки. Проверить также различающиеся материалы корпуса и фасадов.
- Исправлять авторинг и пересобирать GLB, `mesh-source.json`, контракт,
  resize-конфигурацию и UV-привязки. Не компенсировать ошибку ассета специальным
  условием по `modelId` в анимационном runtime.
- Зафиксировать фактические зазоры и положение оси в контракте/паспорте,
  результаты проверок — в отчёте; старые превью помечать как исторические.

В текущем проекте регрессии контролирует
`src/three/furniture/furnitureJoints.test.ts`: raycast по поверхностям ящиков
и проверка пересечения OBB полотен с панелями корпуса через каждые 5°.
Автоматические проверки дополняются визуальным просмотром боковых ракурсов.

## 40. Сменные фасады (v2.18)

**Гладкие, рамочные, вертикально рифлёные и диагональные фасады,
«Ёлочка», «Ромбы» и «Рифлёные края» реализованы для всех девяти шкафов и комодов.** «Марвэл», «Байкал» и «Катания» также имеют «Исходный» стиль:
родной рисунок и сочетание разных панелей. Новые модели требуют собственного
контракта и проверки креплений. В v2.15 «Общая ёлочка» добавлена на шкафы
07/08/09/15; в v2.16 — на комоды 10–14. После визуальной проверки в v2.18
оставлена комодам 12/13. У «Норда», белого комода 10 и «Байкала» 14
остаётся обычная «Ёлочка»: общий вариант не даёт заметного визуального выбора.

Стиль фасада и покрытие — независимые параметры. Один стиль должен работать
с допустимыми цветами и материалами без создания отдельного GLB на каждый цвет.
Дверь или ящик имеет стабильный ID и сборку, включающую панель, декор и ручку;
при открывании все эти части движутся вместе.

| Семейство | Сохраняемые параметры | При изменении размера |
|---|---|---|
| Гладкий | Толщина, кромка, зазоры | Меняется плоскость панели |
| Рамочный / филёнка | Ширина рамки, профиль и глубина | Растёт центральное поле; стыки рамки пересчитываются |
| Вертикальное рифление | Шаг, ширина и глубина канавок | Пересчитывается число повторений и симметричные поля |
| Рифлёные боковые зоны | Шаг, профиль, внешние поля и симметрия | Целые канавки заполняют боковые четверти; средняя половина остаётся гладкой |
| Диагонали, ёлочка, ромбы | Углы, ширина линий, глубина, заданный шаг | Узор строится заново в новых границах |

Не растягивать весь декоративный mesh по двум осям: это меняет профиль, углы
и шаг рисунка. Для каждого стиля объявить допустимые размеры, минимальный
размер центрального поля, поля по краям и правило обработки остатка узора.
Не оставлять случайные узкие обрезки канавок у границы. У короткого фасада
ящика использовать предусмотренный компактный вариант или запретить
несовместимое сочетание с понятным объяснением.

Композиция через несколько створок строится в общей системе координат
**закрытых** фасадов, затем разбивается между локальными сборками створок.
Декор не должен соединять две подвижные части. Швы и межфасадные зазоры
учитываются явно. После открывания и возврата композиция снова совмещается.

Физический масштаб и направление текстур сохраняются отдельно от рисунка
фрезеровки. Геометрия нужна там, где профиль влияет на силуэт, тень и торец;
normal/roughness-карты допустимы для мелкого рельефа после визуальной проверки.
Не запекать освещение или выбранный цвет в универсальную маску узора.

Декор не меняет монтажную плоскость, ось двери и соединение фасада с коробом
ящика. Сохраняются требования раздела 39. Ручки размещаются по монтажным
якорям с проверкой рельефа, свободного пространства и траектории открывания.
Пределы размеров должны учитывать всю сборку, а не только плоскую панель.

Контракт должен задавать stable style ID, параметры профиля,
совместимость, правила размеров/остатков, якоря и границы групп материалов.
При добавлении стиля в сохранения нужен версионированный формат с fallback
для старых ссылок. Сессия v3 и `facadeStyle` сохраняются без смены версии.
Если поле стиля отсутствует в сохранении или ссылке v1/v2/v3, применяется
`defaultStyle` модели: для трёх декоративных моделей это `original`, для
остальных — `smooth`. Прежние размеры и покрытия сохраняются.

Приёмка: base/min/max, промежуточные и асимметричные габариты, короткий ящик,
увеличение и уменьшение обратно, независимая смена покрытия, закрытый,
полуоткрытый и открытый вид, стыки композиции, восстановление сохранения и
ссылки. Паспорт фиксирует число повторений и геометрический бюджет на min/max;
для плотного рифления измеряется стоимость на целевом мобильном устройстве.

### Контракт сменных фасадов

- `assets/source/<model-id>/facade-variants.json` — источник; интеграционный
  генератор переносит его в `FurnitureDefinition.facades` лёгкого каталога.
- `defaultStyle`, `styles` — стабильные ID: `original`, `smooth`, `frame`, `fluted`, `fluted-sides`, `diagonal`, `herringbone`, `diamonds`, `herringbone-wide`.
  `original` доступен только там, где исходная геометрия имеет собственный декор.
  `sourceStyle` указывает стиль исходных детей panel-группы; без поля — `smooth`.
  `defaultStyle` должен сохранять первоначальный вид уже выпущенной модели.
- `targets` — имена центрированных panel-групп с единичным масштабом,
  передняя сторона +Z, базовые размеры, коэффициенты изменения и толщина.
  Для составного фасада это вся группа Front/Panel, включая декоративные
  дочерние детали, но без ручек. Переключение стиля скрывает весь прежний декор.
- `materialSlot` привязывает новые поверхности к существующему покрытию фасадов;
  метрические UV новых поверхностей не получают affine UV старых сегментов.
- `frame` задаёт ширину рамки (45 мм у двери / 28 мм у ящика), глубину 3 мм,
  скос 2 мм и минимальное центральное поле 40 мм. `target.frameWidth` позволяет
  применять 28 мм к ящикам и 45 мм к дверям одного шкафа.
  `target.frameField: "flush"` оставляет центральное поле в монтажной плоскости,
  окружая его углублённой канавкой. Это используется у «Байкала», чтобы
  центральные ручки сохраняли опору. При таком поле внутренний размер
  учитывает два скоса, а не один.
- `fluted` задаёт шаг 20 мм, ширину 6 мм, глубину 1,5 мм; боковые поля
  минимум 18 мм; при краевых ручках поле увеличивается под их крепления
  (45 мм у шкафа 08, 32 мм у «Катании»). Положение сетки по центру неподвижно,
  добавляются пары канавок по краям. `target.flutedClearCenter` исключает целые
  канавки из центральной монтажной полосы, не смещая оставшиеся: у «Байкала»
  защищены 12 мм по центру, чтобы канавка не проходила под опорами ручки.
  Сверху и снизу гладкие поля 20 мм и плавный выход длиной 3 мм.
- `fluted-sides` использует тот же физический профиль `fluted`. Каждая боковая
  четверть фасада заполняется целыми канавками с внешним полем из контракта
  модели. Первая канавка привязана к внешнему краю; следующие идут внутрь
  с постоянным шагом. При увеличении ширины добавляется одновременно по одной
  канавке с каждой стороны. Средняя половина ширины или более широкая полоса
  `flutedClearCenter` остаётся гладкой. Остаток меньше шага добавляется к центру;
  половинок канавок нет. Сужение удаляет те же пары, обратный размер точно
  восстанавливает рисунок. Верхние/нижние поля и места опоры ручек сохраняются.
  Нормали гладкого центра направлены вперёд, соседний рельеф его не искривляет.
  Этот ID обозначает две зоны на каждой отдельной панели, а не общий рисунок
  через несколько дверей. Новые модели должны проверить наличие хотя бы одной
  канавки с каждой стороны во всём диапазоне размеров.
- `diagonal` — отдельная сетка на каждой панели: канавки под углом 45°,
  шаг 80 мм по перпендикуляру, ширина 6 мм, глубина 1,5 мм. Профиль хранится
  в `diagonal`: `pitch`, `width`, `depth`, `margin`, `endMargin`, `minLength`.
  Линия нулевой фазы проходит через центр панели; размер не меняет фазу или
  угол. Центры концов ограничиваются безопасным прямоугольником с учётом
  радиуса, затем добавляются полукруглые окончания. Канавки короче 24 мм
  пропускаются целиком; при обратном размере рисунок восстанавливается.
  Боковые поля соответствуют креплениям модели (18/32/45 мм), торцевые — 20 мм.
  `target.flutedClearCenter` также защищает монтажную полосу этого стиля:
  диагонали заканчиваются перед ней и продолжаются с другой стороны в той же
  фазе. У «Байкала» ширина полосы 12 мм. Обновлённые модели должны проверить
  опоры ручек лучами на min/base/max, а не только визуально по центру ручки.
  UV передней поверхности и диагональных выемок используют метрическую
  проекцию X/Y; направление древесины не поворачивается вместе с канавкой.
  Это проекция покрытия на обработанную панель, без растяжения UV по габаритам.
  Кромка и задняя поверхность имеют собственные метрические проекции.
  Плоские участки имеют нормаль +Z, выемки соединяются с ними без накладных
  деталей. Триангуляция выполняется в точности Float32, совпадающей с GPU,
  чтобы коллинеарные точки не образовывали исчезающие треугольники.
- `herringbone` — зеркальные диагонали на каждой отдельной панели, рисунок
  «Ёлочка». В `herringbone` хранятся те же физические поля, что у `diagonal`,
  плюс `centerGap`: ширина сплошной гладкой полосы по центру, сейчас 12 мм.
  Рабочая полоса — максимум из `centerGap` и `target.flutedClearCenter`.
  Левые линии имеют наклон +45°, правые зеркальны: ширина канавки 6 мм,
  глубина 1,5 мм, шаг 80 мм по перпендикуляру. Расстояние между продолжениями
  вершин вдоль центральной оси — 80√2 ≈ 113,14 мм, это не отдельный шаг.
  Геометрия сначала ограничивает левую сетку безопасным полем, затем создаёт
  её точное отражение. Канавки короче 24 мм удаляются одновременно с зеркальной
  парой. Нельзя независимо округлять количество линий слева и справа.
  Полукруглые окончания сохраняются и у внешнего края, и перед центральной
  полосой: линии не пересекаются и не образуют острые вырожденные вершины.
  Обе стороны используют один профиль и положительный обход граней.
  UV остаются метрической проекцией X/Y: древесина не отражается и не
  поворачивается вместе с направлением канавок. Каждая дверь/ящик получает
  свою ось и свою композицию; общей ёлочки через разные створки здесь нет.
- `herringbone-wide` — общая ёлочка через несколько фасадов. Опциональный стиль
  включается через `styles`; поддержан шкафами 07/08/09/15 и комодами 12/13.
  Использует тот же физический `herringbone`-профиль. По умолчанию начало
  координат — центр полного контура закрытых фасадов, включая ящики.
  `target.compositionGroup` позволяет объявить независимые композиции:
  контур и ось считаются отдельно для каждой группы; между группами линии не продолжаются.
  Отсутствующее поле объединяет все такие панели в одну общую группу.
  Группы задаются контрактом, без распознавания модели/имён mesh в движке.
  Координаты измеряются в системе модели, после resize
  и внутри `motion.withClosedPose`; положение/масштаб модели в сцене,
  камера и угол открывания не влияют на узор.
  Каждая панель получает ширину/высоту композиции и своё смещение от центра
  (`FacadeComposition`, метры). Канавки общей раскладки обрезаются по её
  собственным гладким краевым и монтажным полям. Межпанельные зазоры
  участвуют в координатах, а не вычитаются из шага. Согласованные линии
  продолжаются по обе стороны шва; канавки не пересекают защитные поля.
  Короткие фрагменты менее 24 мм не строятся. Центр композиции сохраняет
  гладкую полосу 12 мм; поля отдельных створок могут образовывать более
  широкую гладкую зону у шва. Рисунок не растягивается вместе с изделием.
  У ящиков остаются собственные панели, задние плоскости и подвижные сборки.
  Приёмка композиции учитывает пропорции и симметрию отдельных блоков.
  Общий центр асимметричного изделия не должен случайно смещать ёлочку
  на блоке ящиков. Можно явно разделить композиции по конструктивным секциям.
  Общий вариант разрешён только при заметной цельной композиции на нескольких
  соседних фасадах. Само число дверей/ящиков не является достаточным условием.
  Не предлагать его на одной колонке ящиков, при практически одинаковом
  результате обычной и общей ёлочки, а также если разделение на группы ради
  баланса убирает заметное различие. У моделей 10/11/14 вариант снят из `styles`.
  Если рисунок выглядит случайно перекошенным или не проходит допустимые
  размеры, сначала исправить композицию, затем включать вариант в каталог.
  Приёмка различимости: обычное расстояние просмотра, закрытые фасады,
  базовые, минимальные, максимальные и промежуточные размеры,
  светлый и тёмный материал. Не включать вариант автоматически по категории.
  Приёмка включает крайние сочетания ширины/высоты, а не только
  одновременное увеличение всех размеров. Короткий ящик проверяется на
  наличие корректных фрагментов, замкнутость и невырожденные треугольники.
  В ключе повторного использования геометрии дополнительно учитываются
  размер общего контура и локальное смещение панели: одинаковые габариты
  не означают одинаковый фрагмент общей композиции.
  Неизвестный стиль и сохранение без стиля используют `defaultStyle`, как и сброс.
  Для явно снятого с выбора стиля допустим `styleFallbacks`: у моделей 10/11/14
  `herringbone-wide` переходит в `herringbone` при загрузке сессии/ссылки.
  Целевой стиль должен входить в `styles`; размеры и покрытия сохраняются.
  `wideDescription` поясняет пользователю композицию конкретной модели.
- `diamonds` — две пересекающиеся сетки ±45° на каждой панели. Шаг 80 мм
  измеряется перпендикулярно канавкам; обе диагонали полного ромба равны
  80√2 ≈ 113,14 мм. Поля `pitch`, `width`, `depth`, `margin`, `endMargin`,
  `fade` хранятся в метрах. Ширина канавки 6 мм, глубина 1,5 мм; профиль
  V-образный с плоскими склонами. Это отдельный профиль, не замена мягких
  канавок диагонального варианта и ёлочки.
  Две канавки образуют общую выемку: на пересечении глубина остаётся 1,5 мм,
  не суммируется. Запрещены наложенные поверхности и сквозные отверстия.
  Сетка привязана к центру панели; изменение размеров меняет её границы,
  сохраняя угол, фазу, шаг и профиль. Боковые/верхние поля наследуются из
  контракта модели. На внутренней границе поля глубина линейно выходит
  к нулю на длине 6 мм (`fade`); обрезанный ромб заканчивается в гладком поле.
  Положительный `target.flutedClearCenter` сохраняет целую монтажную полосу
  под ручками; с обеих сторон полосы также действует выход `fade`.
  Новые вершины от пересечения сетки с полями должны быть включены в обе
  соседние грани: недопустимы T-стыки и вырожденные треугольники.
  UV — метрическая проекция X/Y; направление древесины не поворачивается
  вместе с ромбами. Одна подвижная панель — один замкнутый mesh.
- Новая поверхность располагается внутри прежней панели толщиной 16/18 мм,
  задняя монтажная плоскость неизменна. Наружная кромка 0,7 мм; у «Бруклина» — 0,4 мм, чтобы сохранить
  опору наклонной ручки у верхнего края фасада.
  Плоские зоны рамки имеют плоские нормали, не растянутое затенение скоса.
- `sourceStyle` показывает исходную геометрию вместе с декором. Остальные стили,
  включая гладкий у декоративных моделей, создают один mesh на фасад; прежние
  дочерние детали скрываются. Возврат восстанавливает их исходную видимость. При замене старый BufferGeometry
  освобождается. Число активных геометрий не растёт при повторных сменах.
- Одинаковые панели текущей модели могут использовать общий неизменяемый
  BufferGeometry; mesh, материал и подвижная сборка остаются отдельными.
  Ключ повторного использования учитывает размер, толщину, стиль, параметры
  рамки и монтажные поля. Не хранить историю геометрий всех пройденных размеров.
  Общая геометрия освобождается один раз после исчезновения последнего
  использования. При перестроении узора проверять время расчёта на высоких
  дверях и промежуточных размерах, отдельно от качества неподвижного кадра.
- Ширина/высота меняют геометрию внутри существующей подвижной сборки.
  Открывание, ручки, IDs, view «Наполнение» и стыки раздела 39 сохраняются.

Все текущие min/base/max поддерживаются. Комбинированный вариант:
[combined-facades-v1-validation.md](combined-facades-v1-validation.md).

## 41. Камера и физический масштаб (v2.10)

Геометрия измеряется в метрах и не нормализуется под экран. Ракурс не является
единицей измерения: перспективное изображение зависит от расстояния и угла.

- Шкафы используют общий максимальный габарит каталога и общий ракурс, чтобы
  смена модели или размеров не меняла камеру при сравнении.
- Комод имеет собственный сохранённый ракурс в текущем просмотре. Его
  исходное расстояние рассчитывается по максимальным габаритам этой модели,
  а цель вращения/приближения — половина текущей высоты корпуса.
- При изменении высоты комода камера и цель смещаются на одну и ту же величину.
  Орбита, пользовательское смещение цели и расстояние сохраняются. Изменение
  ширины/глубины не подгоняет масштаб автоматически.
- При возврате восстанавливается ракурс выбранного комода, общий ракурс шкафов
  или ракурс столов. После изменения размера viewport активный вид вписывается
  заново; кэш остальных видов корпусной мебели сбрасывается.
- Камера не входит в сохраняемую конфигурацию/ссылку. При загрузке страницы
  применяется начальный ракурс выбранной модели; PNG использует текущий.

Приёмка: шкаф → низкий широкий комод → узкий высокий комод → шкаф, умеренное
приближение к центру корпуса, изменение высоты без смены расстояния, desktop
и portrait viewport. Проверять низ изделия и подвижные части.

# Паспорт модели — обязателен для каждого GLB

Каждый передаваемый GLB сопровождается этим паспортом.

## Model

Человекочитаемое название модели.

## Model ID

Стабильный ID проекта, например:

```text
table-01
wardrobe-02
dresser-01
```

## Type

```text
constructor-ready
static-ready
```

## Runtime compatibility

Одно из:

```text
Supported by current engine
Requires engine extension
```

Если требуется расширение, перечислить точное отсутствующее поведение.

## Base dimensions

Финальные внешние размеры экспортированной модели:

```text
Width × Depth × Height
```

или другие semantic dimensions, подходящие конкретному объекту.

## Front direction

Например:

```text
+Z
```

или:

```text
N/A — rotationally symmetric
```

## Configurable parameters

Например:

```text
length
width
height
diameter
```

Указываются только параметры, которые предполагается изменять **в нашем конфигураторе**.

## Limits

Для каждого configurable parameter:

```text
base
min
max
step
```

## Dimension mapping

Например:

```text
length -> X
width  -> Z
height -> Y
```

Для круглого объекта:

```text
diameter -> X + Z
```

## Resize anchors

Например:

```text
length -> center
width  -> center
```

## Node structure

Список основных управляемых Nodes/Groups.

Пример:

```text
Table_Root
TableTop
Leg_01
Leg_02
Leg_03
Leg_04
```

## Controlled behavior

Для каждой управляемой детали указать одно или несколько:

```text
Fixed
Scale
Edge-anchor move
Delta move / spread
Stretch segment
Fit between anchors
Visibility / variant
Reconfigure
```

Пример:

```text
TableTop:
  length -> Scale local X
  width  -> Scale local Z

Leg_01..Leg_04:
  length -> Edge-anchor move X
  width  -> Edge-anchor move Z
```

## Hierarchy notes

Указать parent/group relationships, важные для runtime transforms.

## Local-axis notes

Для наклонных или повернутых элементов указать local axis, представляющую физическую продольную длину.

## Profile-resize behavior

Одно из:

```text
Uniform scaling acceptable
Preserve fixed end radius
Preserve fixed corner radius
Segmented resize required
Custom geometry behavior required
```

## Height readiness

Для каждой модели стола указать одно из:

```text
height-configurable
height-ready
height-fixed
```

Для `height-configurable` и `height-ready` дополнительно указать:

```text
semantic height dimension
base/min/max/step, если уже известны
vertical support targets
local longitudinal axis
baseLength каждого растягиваемого сегмента
floor anchor
верхние детали, перемещающиеся вместе со столешницей
```

## Tabletop thickness readiness

Указать одно из:

```text
thickness-configurable
thickness-ready
thickness-fixed
```

Если изменение толщины предусмотрено, указать:

```text
semantic dimension
base/min/max/step
local scale axis
anchor: bottom-surface / top-surface / center / custom
связанные moving targets
UV behavior торцевых поверхностей
```

## Material names

Точные экспортированные `material.name`.

Пример:

```text
Top_Surface
Bottom_Surface
Top_Edge_Long
Top_Edge_Short
Metal_Frame
```

## Replaceable finish groups

Указать slots, которые должны меняться вместе при выборе finish.

Пример:

```text
PrimaryTop:
  Top_Surface
  Bottom_Surface
  Top_Edge_Long
  Top_Edge_Short
```

## UV behavior

Для каждого динамического material surface:

```text
physical dimension -> texture axis
```

Пример:

```text
Top_Surface:
  length -> U
  width  -> V

Bottom_Surface:
  length -> U
  width  -> V

Top_Edge_Long:
  length -> U

Top_Edge_Short:
  width -> U
```

Также указать UV anchor, если он не centered.

## Pivot behavior

Указать pivots, необходимые для:

- дверей;
- ящиков;
- вращающихся элементов;
- перемещаемых опор;
- специальных resize groups.

## Scene requirements

Обычно:

```text
Uses shared configurator scene/environment.
No asset-specific lights/camera/HDRI.
```

Если ассету требуется особый rendering behavior, это указывается отдельно.

## Performance

По возможности:

```text
GLB size:
Triangles:
Meshes:
Materials:
Texture resolutions:
```

## Notes for Three.js

Любая важная информация для интегратора, которая неочевидна из имён и rules.

# Рекомендуемый handoff для runtime-config

Вместе с паспортом предоставляется краткое machine-oriented предложение, которое можно преобразовать в проектный `FurnitureDefinition`.

Пример:

```text
modelId: table-example
modelUrl: /models/table-example.glb

dimensions:
  length: base/min/max/step
  width:  base/min/max/step

rules:
  TableTop:
    length -> Scale X
    width  -> Scale Z

  Support_Left:
    length -> EdgeAnchor X

  Support_Right:
    length -> EdgeAnchor X

textureAxes:
  Wood_Top:
    length -> U
    width  -> V
```

Это не заменяет настоящий TypeScript-конфиг, но устраняет неоднозначность между созданием ассета и интеграцией.

## 41. Сглаживание декоративных фасадов в движении (v2.18)

Разные ракурсы и положения мебели не смешиваются. Подкадры для движущегося
изображения снимаются в одном состоянии сцены. После изменения камера,
геометрия и видимость сбрасывают накопленный результат до нового вывода.
Толщина, рисунок фасада и полноразмерные PBR не меняются ради сглаживания.

Дополнительные проходы ограничиваются по наблюдаемому темпу кадров.
Уточнение после остановки остаётся ограниченным 16 образцами и прекращается
в простое. Цвет усредняется в линейном пространстве без повторного tone mapping.
Проекция камеры восстанавливается и после исключений; выбор деталей и PNG
должны использовать актуальное состояние. Проверять ограничения памяти,
отсутствие float attachments, resize, смену стиля, экспорт и освобождение ресурсов.

Число автоматических тестов не подтверждает FPS, нагрев или отсутствие муара
на физическом телефоне. Ограничения и порядок проверки:
[motion-antialiasing-v1.md](motion-antialiasing-v1.md).

## 42. Экранная детализация мелкого рельефа (v2.19)

Полная геометрия остаётся эталоном размеров, конструкции и ближнего вида.
Для углублений сменных фасадов разрешено плавное GPU-ослабление глубины и
наклона нормалей, когда канавка становится субпиксельной. Это приближённый
визуальный LOD, а не изменение толщины изделия или выбранного материала.

- Размер детали оценивается в физических пикселях с учётом проекции и
  положения движущейся дверцы; одной мировой дистанции недостаточно.
- Переход непрерывный. Нет пересоздания геометрии на каждом движении камеры,
  скачков числа полос или размытия всей сцены. Вблизи профиль исходный.
- Тени имеют совместимые depth/distance шейдеры. Их фильтрация рассчитывается
  по разрешению карты и камере света; все custom-материалы освобождаются.
- Метрические UV, задние плоскости, монтажные плоскости и наружные фаски
  сохраняются. Скрытые исходные детали продолжают поддерживать resize.
- Для исходного GLB требуется явный `facades.sourceRelief: { width, depth }`
  в метрах, синхронный в facade-variants.json, catalog и runtime-конфигурации.
  Сейчас этот контракт применён к «Катании»: 0.003 / 0.0018 м.
  Он поддерживает только углублённый вертикальный профиль без наружной фаски
  в осевых дочерних сетках panel; положительные локальные масштабы допустимы.
  Нельзя автоматически применять контракт к накладным рейкам, повёрнутым
  частям, произвольной фрезеровке или собственному шейдеру другого ассета.
- Далёкий вид, вращение, возвращение ближнего вида, крайние размеры, белый/
  графит/дерево и открытые двери входят в визуальную приёмку. Unit-тесты и
  программный OpenGL не заменяют проверку полного viewer на устройстве.
- Экспорт PNG декоративного фасада завершает отдельную статическую серию,
  фиксируя одну позу. Ограничения памяти/возможностей сохраняют обычный
  экспорт без обещания 16 образцов на неподдерживаемом устройстве.

Подробности: [relief-filter-v1.md](relief-filter-v1.md).

## 43. Прямая модульная гардеробная v1

В дополнение к GLB-каталогу допускается процедурная сборка из типовых панелей
с отдельным контрактом. Одна единица сцены = 1 метр. Режим `wardrobe` не
подменяет модели готовых шкафов и не меняет их размеры/ракурсы.

- Прямой ряд 1–6 самостоятельных секций; у соседей две собственные боковины.
  Общие перегородки не подразумеваются. Порядок задаётся массивом, идентичность
  секций сохраняется по стабильным ID при перестановке.
- Пол y=0; задние поверхности на общей плоскости; общая ширина — сумма ширин,
  высота/глубина — максимум. Передние края секций разной глубины различаются.
- Боковины, верх, дно, полки, цоколь: 16 мм; задняя стенка: 4 мм;
  высота цоколя: 70 мм. Эти значения не растягиваются вместе с габаритами.
  Верх/дно/задник заполняют промежуток между боковинами. Полки имеют боковой
  зазор 1 мм и отступ 25 мм от переднего края.
- Прототип: ширина 400–1000 мм / шаг 50; высота 800–2800 / шаг 100;
  глубина 400–800 / шаг 50. Это ограничения конфигуратора, не производственная
  проверка нагрузки, пролётов полок, крепежа и устойчивости изделия.
- Без штанги: до 6 полок с равными свободными промежутками, минимум 200 мм
  между поверхностями (включая дно/верх). Со штангой: без полок, верхняя полка
  или верхняя и нижняя полки. От верхней поверхности полки/дна под штангой
  до нижнего края штанги — минимум 600 мм. Допустимое количество полок зависит
  от высоты секции; при уменьшении высоты лишние полки удаляются, возвращение
  высоты не восстанавливает их автоматически. Диаметр штанги 25 мм; от глубины
  500 мм она поперечная, при меньшей глубине — торцевая с двумя опорами.
- Плиты имеют метрические UV с сохранением направления волокон. Используются
  общие PBR; изменение габаритов не растягивает изображение текстуры.
- Генератор загружается по требованию. Одинаковые геометрии переиспользуются,
  удалённые освобождаются; асинхронная смена материалов применяет только
  актуальный запрос, а не результат устаревшей загрузки.
- Сохранение сессии v4 и ссылки `kind: wardrobe-assembly`; сессии v1–v3
  мигрируют без потери настроек каталога и столов. Сброс относится только
  к активной сборке. Камера и расширенная область студии принадлежат этому режиму.

- Исходный корпус/полки — «Серый нейтральный». Сохранённые покрытия не
  перезаписываются; reset активной сборки восстанавливает новые defaults.
- «Вернуть общий вид» возвращает исходный ракурс и охватывает фактические
  габариты всей сборки. Изменение размеров само по себе не меняет зум.

Детальный контракт: [wardrobe-assembly-v1.md](wardrobe-assembly-v1.md),
[уточнения и будущие ограничения](wardrobe-refinements-v1.md).

Зафиксировано для следующего этапа (пока не реализовано): отдельные материалы
секций с наследованием общего покрытия; высоты отдельных полок и штанги
с шагом 50 мм. Сетка перемещения задаёт положение детали, а проверка зазоров
учитывает её толщину/диаметр. Минимумы 200/600 мм относятся к свободному
пространству. Недопустимые позиции нельзя предлагать; несовместимое уменьшение
корпуса должно обрабатываться явно, без скрытых пересечений.
Ящики, фасады, ручки, общие перегородки, углы и Г-/П-компоновки требуют
следующих контрактов; наличие GLB готового шкафа их автоматически не задаёт.

# Финальное правило

**Категория мебели никогда сама по себе не определяет поведение.**

Стол может иметь:

- одну опору;
- две опоры;
- четыре ножки;
- фиксированный pedestal;
- pedestal, который разделяется;
- U-frame;
- наклонные V/Y supports;
- круглую, овальную, capsule или прямоугольную столешницу;
- ни одного конфигурируемого размера;
- один конфигурируемый размер;
- несколько конфигурируемых размеров.

Тот же принцип применяется к шкафам, комодам и всей будущей мебели.

Ассет проектируется согласно **конкретному runtime-контракту конкретной модели**.

Если общее правило стандарта конфликтует с правильной физической конструкцией или предполагаемым configurator behavior конкретной модели, исключение должно быть выявлено **до моделирования**, описано в паспорте и отражено в TypeScript model config.
