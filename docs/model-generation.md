# Генерируемые данные моделей

Каталог шкафов и комодов разделён на лёгкий `catalog.ts` и загружаемый по
требованию `runtime.ts`. Большие `config.ts` и `textureTransforms.ts` содержат
числовые правила изменения размеров, привязки текстур и имена деталей.
Их объём сам по себе не означает сложную исполняемую логику.

## Источники и результаты

| Область | Источник | Результат |
| --- | --- | --- |
| Геометрия модели | `assets/source/<model>/model-spec.json`, `build_model.mjs`, текстуры | GLB, `model-contract.json`, исходная проверочная `config.ts` и отчёты |
| Шкафы 07–09 | `assets/source/wardrobes-integration/generate_runtime.py`, проверочная конфигурация, контракт, `facade-variants.json` | `catalog.ts`, `runtime.ts`, `textureTransforms.ts` для трёх шкафов |
| Комоды 10–14 | `assets/source/dressers-integration/generate_runtime.py`, те же виды исходных данных | Такие же три файла для пяти комодов |
| «Катания», модель 15 | Собственный `build_model.mjs`, `model-spec.json`, `facade-variants.json` | Конфигурация с UV-таблицами внутри, каталог и runtime вместе с GLB |

Базовые размеры относятся к исходной геометрии GLB. Начальный выбор, если он
отличается, задаётся через `defaultValue`; его нельзя менять подменой `base`
без соответствующего обновления геометрии. У «Катании» текущая исходная и
начальная глубина — 450 мм.

## Проверка без перезаписи

Из корня проекта, с Python 3.12 (в Windows команда может называться `py -3`):

```bash
python assets/source/wardrobes-integration/generate_runtime.py --check
python assets/source/dressers-integration/generate_runtime.py --check
```

Команды сравнивают все 24 результата с тем, что сейчас выдают генераторы.
Отсутствующий или изменённый файл даёт код завершения 1 и список путей.
LF и CRLF считаются одинаковыми; проверка не переписывает файлы.
При несовпадении нужно исправить источник или запустить соответствующий
генератор без `--check`, затем проверить diff. Все входные данные читаются
до начала записи, поэтому ошибка в одном из них не оставляет частично
обновлённый каталог. Это не транзакционная запись при сбое диска.

Python нужен только для этих генераторов и их проверок. Установка зависимостей
сайта, обычная сборка Vite и опубликованное приложение его не требуют.
Новые Python-пакеты не нужны: используется стандартная библиотека.

## Что проверяет CI

- Режим `--check` для трёх шкафов и пяти комодов.
- Три проверки CLI в изолированных временных папках: устаревшие и отсутствующие
  результаты, CRLF, отказ от частичной перезаписи при повреждённом входе.
- Vitest сверяет все девять моделей с исходными параметрами, контрактами UV,
  списками материалов и рисунками фасадов. У «Катании» включены UV рифления.
- Проверка статических импортов от `src/main.tsx` запрещает попадание тяжёлых
  определений этих моделей в начальную загрузку приложения. Динамический импорт
  остаётся границей ленивой загрузки.
- Существующие тесты реальных GLB проверяют размеры, толщины, UV и движение.

`--check` **не перестраивает GLB** и не доказывает побайтовую воспроизводимость
всей цепочки авторинга. Для изменения самой модели нужны зависимости её
`assets/source/<model>/package.json`, запуск `build_model.mjs` и проверки
получившейся геометрии. У «Катании» отдельного Python-генератора нет;
согласованность её готовых данных проверяет Vitest.

## Результат аудита 16 ноября 2026 года

Повторная генерация интеграции восьми моделей совпала с 24 текущими файлами.
Параметры, фасады и UV «Катании» соответствуют исходным JSON. Каталоги уже
отделены от тяжёлых определений; ручное дробление числовых таблиц не требуется.
На этом этапе меняются инструменты проверки, а не модели или ресурсы сайта.
Это защита от рассогласования при следующих изменениях, не оптимизация FPS.
