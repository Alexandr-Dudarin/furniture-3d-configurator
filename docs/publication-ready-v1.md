# Исторический отчёт: подготовка публичного демо / publication-ready-v1

Дата: 2026-10-01. База: принятый `wardrobe-u-shape-v1` / стандарт v2.37.
> Этот документ фиксирует подготовительный этап 1 октября 2026 года, до
> публикации и отдельной очистки Git-истории. Приведённые размеры, команды
> переноса файлов и сведения об истории относятся к тому снимку проекта.
> Демо уже опубликовано: [открыть сайт](https://furniture-3d-configurator-kappa.vercel.app/).
> Актуальные команды и настройки: [развёртывание и CI](deployment.md).

## П-образная сборка

В каждой из трёх сторон должна оставаться хотя бы одна обычная секция.
На центральной стороне А минимум — одна секция шириной 400 мм. Два угла
добавляют по 500 мм возврата: между корпусами противоположных рядов
получается минимум 1400 мм. Закрытые фасады и выступающие ручки учитываются
отдельно в показанном в интерфейсе проходе.

Ширина одной дверцы ограничена 600 мм, у более широкой секции две створки.
Ящики выдвигаются на 72% глубины своего короба. Кроме этих ограничений
действуют проверки траектории: неподвижное препятствие ограничивает угол
или ход; конфликтующая открытая деталь сначала закрывается. Проверяются
все три стороны и оба угла, включая противоположный ряд. «Открыть всё»
оставляет открытыми совместимые детали. Геометрию этого этапа менять не понадобилось.

`assets/` с исходными моделями и техническими материалами занимает около
200 МиБ, но не входит в `dist/` и исключён из CLI-загрузки. `node_modules/`
устанавливается на сервере, не коммитится и не загружается с компьютера.
Исходные модели остаются в Git для воспроизводимости проекта.
Полный объём сайта не равен объёму первой загрузки браузера: модели и
соответствующие runtime-модули загружаются по выбору пользователя.

## Первый стол: сохранить и убрать из публичных ресурсов

После распаковки обновления выполнить из корня проекта:

```powershell
node scripts/archive-first-table.mjs
if ($LASTEXITCODE -ne 0) { throw "Стол не архивирован; остановитесь и проверьте сообщение" }
```

Команда сохраняет `first-table.glb`, копию `config.ts`, инструкцию и SHA-256
в `.local-archive/first-table/`. Только после проверки копии удаляется GLB
из `public/models/`. Различающиеся существующие копии не перезаписываются.
Повторный запуск безопасен. В чистом checkout без исходного GLB команда
сообщает, что локального архива нет: удалённый репозиторий его не хранит.

Локальный архив игнорируется Git и Vercel. Конфигурация в
`src/three/models/first-table/config.ts` остаётся лёгким примером реализации
и используется тестами универсального контроллера. Два теста настоящего
GLB используют архив, если он есть; в чистом checkout только они пропускаются.
Остальные проверки контроллера, материалов и действующих моделей выполняются.

Архив остаётся на диске. Его стоит скопировать на резервный носитель:
Git-игнорирование не является резервным копированием. После коммита
публичный GLB исчезнет из текущей версии репозитория, но останется в прошлых
коммитах, если уже был там. История не переписывается и force-push не требуется.

Для возврата GLB на компьютер:

```powershell
node scripts/archive-first-table.mjs --restore
```

Резервная копия сохраняется. GLB можно открыть в Blender. Для возвращения
именно в локальный каталог дополнительно импортировать `FIRST_TABLE_CONFIG`
из `../three/models/first-table/config` в `src/configurator/furnitureRegistry.ts`
и добавить `[FIRST_TABLE_CONFIG.id, FIRST_TABLE_CONFIG]` в Map. Для просмотра
запустить `npm run dev`; начальную модель менять необязательно. Перед следующей
публикацией снова убрать регистрацию и запустить архивирование. `prebuild`
останавливает публикационную сборку, если тяжёлый GLB снова попал в `public/`.

## Проверка и коммит

Полные команды и точный список файлов лежат в локальной инструкции
`docs/updates/publication-ready-v1.md`. В список коммита включено удаление
`public/models/first-table.glb`. Не добавлять `.local-archive/` принудительно.
Старые checker-скрипты этапов больше не являются проверкой текущего состояния;
для этого обновления используется `check-publication-ready-v1.cjs`.

Проверено: 675 тестов / 83 файла, сборка TypeScript/Vite, ESLint изменённых
TS-файлов, побайтовое совпадение всех публичных ресурсов с `dist/`.
Дополнительно сборка прошла из отдельной копии только разрешённых для Vercel
исходников — без `assets/`, `docs/`, архива и прежнего `dist/`.
В этой копии отдельно прошли 9 тестов контроллера/материалов; 2 архивных
GLB-теста ожидаемо пропущены. Это не проверка WebGL на телефоне или работающего Vercel.

## Публикация через GitHub и Vercel

1. Применить обновление, архивировать стол, проверить сайт и создать коммит.
2. Посмотреть `git remote -v` и `git branch --show-current`. Если remote уже
   настроен, использовать именно его. Для нового репозитория создать пустой
   репозиторий GitHub без дополнительного README; адрес и ветку подставлять
   только после проверки, не менять существующий `origin` вслепую.
3. Отправить проверенную ветку в GitHub. Полный локальный архив проекта
   для этого не нужен. Git-история может быть больше файлов текущей версии.
4. В Vercel импортировать этот репозиторий. Framework — Vite, Root Directory —
   корень проекта, Install Command — `npm ci`, Build Command — `npm run build`,
   Output Directory — `dist`. Подойдёт поддерживаемый Vercel Node.js 22.x
   (Vite требует 22.12+) или 24.x. Ключи API и отдельный backend здесь не нужны.
5. Установить выбранную проверенную ветку как Production Branch. После
   развёртывания отправлять работодателю основной Production URL.
6. Открыть Production URL в инкогнито без входа в Vercel. Проверить каталог,
   гардеробную, сохранённую ссылку, перезагрузку этой ссылки и экспорт PNG.
   Если вместо проекта требуется вход, проверить Deployment Protection.

`vercel.json` направляет старые `/feedback/...`, `/catalog/...` и `/viewer/...` ссылки на
приложение. Корневые ссылки с `?config=...` также работают. Пути отсутствующих
GLB и текстур не переписываются на HTML: ошибку ресурса можно диагностировать.
LocalStorage привязан к домену; настройки с localhost сами на новый адрес
не переедут. Для переноса скопировать конфигурационную ссылку и заменить её
origin на опубликованный адрес, сохранив `?config=...`.

## Что означают ограничения сервисов

По документации, проверенной 2026-10-01:

- Vercel ограничивает загрузку исходников через CLI: Hobby — 100 МБ,
  Pro — 1 ГБ. Это не универсальный предел размера Git-репозитория.
  Наш разрешённый для загрузки набор укладывается даже в 100 000 000 байт;
  `npm run check:publication` пересчитывает его после изменений.
- GitHub блокирует обычные Git-файлы больше 100 МиБ. В текущем снимке
  таких файлов нет; ограничение применяется к одному файлу. История
  локального `.git` в переданных исходниках отсутствует и отдельно не проверена.
- Hobby рассчитан на личное некоммерческое использование. Для портфолио
  можно начать с него в пределах квот; для коммерческого сервиса — Pro.
